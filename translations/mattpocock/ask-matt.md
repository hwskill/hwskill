# 询问 Matt

你不需要记住每项技能，直接询问即可。

**流程（flow）**是一条穿过多项技能的路径。多数路径沿一条**主流程**推进，两条**入口路径**会汇入其中。其余技能要么独立使用，要么作为底层词汇层运行。

## 主流程：从想法到交付

大多数工作的路径：你有一个想法，并希望把它构建出来。

1. **`/grill-with-docs`**通过访谈明确想法。只要你**位于工作目录中**，就从这里开始：它有状态，会把学到的内容保存在 `CONTEXT.md` 和 ADR 中。（没有工作目录时改用“独立技能”中的 `/grill-me`。两者使用相同的 `/grilling` 原语；只要存在仓库，`grill-with-docs` 会留下过程记录，因此更合适。）
2. **分支：能否在对话中解决所有问题？**如果某个问题需要可运行的答案（状态、业务逻辑或必须实际查看的 UI），就绕行原型；原型位于独立目录，因此两个方向都用 **`/handoff`** 衔接（参见“阶段边界”）：
   - 用 **`/handoff`** 导出，然后针对该文件开启全新会话；
   - 用 **`/prototype`** 通过可丢弃代码回答问题；
   - 再用 **`/handoff`** 把结论带回来，并从原始想法会话中引用。
3. **分支：这是否是跨多个会话的构建？**
   - **是** → 使用 **`/to-spec`**（把会话转换为规格），再使用 **`/to-tickets`** 拆成曳光弹工单，每张声明自身的**阻塞边**。在本地跟踪器中，每张工单位于 `.scratch/<feature>/issues/` 下的独立文件，人工按阻塞项优先处理；在真实跟踪器中，边会转换成原生阻塞链接，因此任何阻塞项已完成的工单都可领取：每张工单各自启动 **`/implement`**，并在工单之间使用 **`/clear` 清空上下文**。每张工单都自包含，因此最后一张工单的上下文也可以丢弃。
   - **否** → 在当前上下文窗口直接使用 **`/implement`**。

   两种情况下，**`/implement`** 都会在内部驱动 **`/tdd`** 构建每张 issue（每次一个红绿切片），然后在提交前运行 **`/code-review`**，从标准和规格两个轴评审 diff。只希望按测试优先构建具体行为、不需要完整规格时可单独使用 **`/tdd`**；希望相对固定点评审分支或 PR 时可单独使用 **`/code-review`**。

### 上下文卫生

步骤 1–3 应保持在**一个连续的上下文窗口**中（在 `/to-tickets` 完成前不要压缩或清空），使追问、规格和工单建立在同一思考基础上。随后每次 `/implement` 都使用全新上下文，只根据工单工作。

限制来自 [smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)：在这个窗口内（先进模型约 15 万 token）模型仍能保持清晰推理。如果会话在 `/to-tickets` 前接近上限，不要在能力下降的状态继续；应在最近的阶段边界执行 `/compact` 后继续（参见“阶段边界”）。

## 入口路径

入口路径从一种会产生工作的初始情况开始，随后汇入主流程。

- **缺陷和请求不断积压** → **`/triage`**。它让 issue 在分诊角色中流转并生成 Agent 可执行的 issue，之后由 **`/implement`** 领取。

  分诊只用于**并非由你创建**的 issue：缺陷报告、传入的功能请求以及其他原始请求。`/to-tickets` 生成的工单已经可由 Agent 执行，因此**不要再次分诊**。

- **某些功能损坏** → **`/diagnosing-bugs`**。用于困难问题：初看无法解决的缺陷、间歇性不稳定、在两个已知正常状态之间引入的回归。它在获得**紧密反馈循环**（一条能在**这个**缺陷上变红的命令）前拒绝提出理论，随后用回归测试修复。若事后分析发现没有合适接缝来锁定缺陷，就交给 **`/improve-codebase-architecture`**。

- **规模巨大且方向模糊的工作：全新项目或无法在一次会话中处理的大型功能** → **`/wayfinder`**，这是这里认知负担最高的流程。看不清从现状到目标的路径时，它会在 issue 跟踪器上绘制由**决策工单**组成的**共享地图**，逐项解决，持续产出**决定，而不是交付物**，直到迷雾后退、道路清晰。`/grill-with-docs` 用于单次会话可以容纳的想法，wayfinder 用于无法容纳的想法；它更慢、更密集，只应在这种情况使用，绝不用于范围清晰的功能。

  地图变清晰后，**它负责交接而不是构建**：在 **`/to-spec`** 汇入主流程，把地图中相互链接的决定压缩成可构建计划，然后照常使用 `/to-tickets` 和 `/implement`。直接从地图进入 `/implement` 会跳过压缩并丢失关联细节；只有工作实际很小时才可直接进入 `/implement`。

## 代码库健康

这不是功能开发，而是维护。

- 有空时运行 **`/improve-codebase-architecture`**，使代码库保持适合 Agent 操作。它会找出**加深机会**；选择一项就会产生一个想法，可带入主流程的 `/grill-with-docs`。它负责勘察和寻找候选项；下文的 **`/codebase-design`** 是设计选中候选项的工作台。

## 底层词汇

两项由模型调用的参考技能运行在其他技能**之下**，各自是其词汇的单一事实来源。当问题在于**用词**而不是流程时可直接使用，也可让上层技能自行加载。

- **`/domain-modeling`**：明确项目的**领域**语言：质疑模糊术语、解决一词多义（例如 “account” 同时承担三种含义），把难以撤销的决定记为 ADR。`/grill-with-docs` 会主动采用这项纪律，使 `CONTEXT.md` 保持为干净词汇表。
- **`/codebase-design`**：提供深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块**形态**：在干净接缝处，用小接口隐藏大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这些词汇。

## 阶段边界

**阶段**是一次会话内的一段工作，例如追问、实现、QA。在两个阶段的**边界**有五种选择；选择本身是整张地图中最模糊的决定：

- **继续**：留在当前会话。没有成本，也不丢失内容。
- **`/clear`**：下一阶段不需要当前信息时，清空窗口。
- **`/handoff`**：写出可移植 Markdown 文件。适用范围很窄：新的运行环境、新目录、同事，或在阶段中途分叉支线任务。它带来的价值是可移植性。
- **子 Agent**：把范围明确的任务发送到独立窗口，并收回报告。
- **`/compact`**：压缩当前上下文，用压缩内容启动新会话。它是决策树底部的**默认选择**，而不是第一选择。

完整有序决策树见 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)：五个问题、各分支理由，以及一手资料成本为何使**继续**成为最先排除的选项。决定应在阶段**边界**作出；阶段中途应继续，或把剩余工作拆给子 Agent。

## 独立技能

这些技能完全位于主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 相同的持续访谈，但**无状态**：不在本地保存内容，也不构建 `CONTEXT.md`。**不在工作目录中**时使用，例如明确计划、设计、文章或其他没有仓库的内容。位于工作目录时使用 `/grill-with-docs`，因为它执行相同访谈并留下记录，因此更合适。
- **`/grilling`**：访谈原语本身，包括轮次、前沿、事实由 Agent 查找而决定由用户作出。`/grill-me` 和 `/grill-with-docs` 是两个具名入口；`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 也会在内部使用它。只有希望得到没有包装层的访谈时才直接调用。
- **`/resolving-merge-conflicts`**：逐个冲突块处理正在进行的 merge 或 rebase，通过追溯双方一手资料按**意图**解决，而不是直接选择代码行，最后完成操作。它绝不运行 `--abort`。该技能独立于所有流程；已处于冲突中时使用。
- **`/prototype`**：用小型可丢弃程序回答一个设计问题，例如状态模型是否合理，或 UI 应该是什么样。可丢弃约束的是代码写法，并不承诺销毁：答案会进入真实代码，原型本身作为**一手资料**保留在从 main 分出的 `prototype/<name>` 分支，并由实现 issue 指向它。它是主流程步骤 2 的绕行路线，也适用于任何难以在纸面确定的设计问题。
- **`/research`**：把阅读工作委派给**后台 Agent**。它根据**一手资料**调查问题，并在仓库中留下带引用的 Markdown 文件。阅读期间继续其他工作。该文件应带入 `/grill-with-docs` 的主流程，因为调研支持思考，而不是替代思考。
- **`/to-questionnaire`**：阻塞信息不在用户脑中或代码库、而在**其他人**那里时使用。它生成问卷供对方填写。它与 `/grill-me` 相反：不访谈用户关于主题，而是询问**如何发送**（发给谁、需要收回什么），再把问题对准知识缺口。返回内容可供 `/grill-with-docs` 或 `/to-spec` 使用。
- **`/wizard`**：用于只有**人**能执行的步骤，例如配置基础设施、设置凭据或 CI secrets、操作陌生的第三方后台、运行一次性迁移或切换。它生成交互式 Bash 脚本，依次打开 URL、采集值并写入 `.env` 和 GitHub secrets，使流程不必每次都重新向 Agent 解释。它由模型调用，Agent 一旦遇到只有用户能跨越的障碍就应使用。如果 Agent 自己能完成，就应自行执行；该技能只用于确实需要人在回路中的情况。
- **`/wait-what`**：用于纠正没有解释清楚的消息。在任何技能中途使用，Agent 会补充缺失上下文，以通俗英语重新表达，并使用 `CONTEXT.md` 的词汇。它在事后工作；`/grill-with-docs` 是事前预防，因为尽早约定共享语言能防止术语突然出现。
- **`/teach`**：以当前目录作为有状态工作区，跨多个会话学习概念。
- **`/writing-for-agents`**：编写供 Agent 使用的文档时参考，包括技能、`AGENTS.md` 和指向的文档。

## 前置条件

**`/setup-matt-pocock-skills`**：第一次运行工程流程前先执行，配置其他技能依赖的 issue 跟踪器、分诊标签和文档布局。也支持自定义 issue 跟踪器。
