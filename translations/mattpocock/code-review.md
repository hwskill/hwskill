对用户给出的固定点与 `HEAD` 之间的 diff 做双轴评审：

- **标准（Standards）**：代码是否符合仓库记录的编码标准？
- **规格（Spec）**：代码是否忠实实现了原始 issue 或规格？

两个轴由**并行子 Agent**执行，避免相互污染上下文；随后汇总发现。

issue 跟踪器信息应已提供。如果缺少 `docs/agents/issue-tracker.md`，提示用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比较点

用户所说的任何值都可以作为固定点，例如提交 SHA、分支名、标签、`main` 或 `HEAD~5`。用户没有指定时就询问。

只记录一次 diff 命令：`git diff <fixed-point>...HEAD`（三点语法，以 merge-base 为比较基础）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续前确认固定点可解析（`git rev-parse <fixed-point>`），并确认 diff 非空。无效引用或空 diff 应在这里失败，不要让问题进入两个并行子 Agent。

### 2. 找出规格来源

按以下顺序寻找原始规格：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），按 `docs/agents/issue-tracker.md` 中的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 都找不到时，询问用户规格在哪里。如果用户说没有规格，**规格**子 Agent 跳过并报告“没有可用规格”。

### 3. 找出标准来源

查找仓库中说明代码应如何编写的所有文件，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库自身文档外，标准轴始终携带以下**代码气味基线**：Fowler《重构》第 3 章中的固定代码气味集合，即使仓库没有文档也适用。它受两条规则约束：

- **仓库规则优先。**仓库记录的标准始终优先；它明确认可某项做法时，不报告相应气味。
- **始终属于判断。**每种气味都是带标签的启发式判断（如“可能存在 Feature Envy”），而不是硬违规。与其他标准一样，跳过工具已经强制检查的内容。

每项气味按“含义 → 修复方式”描述，应对照 diff 检查：

- **含义不明的名称（Mysterious Name）**：函数、变量或类型名没有说明其作用或内容。→ 重命名；如果无法起出诚实名称，说明设计仍不清晰。
- **重复代码（Duplicated Code）**：相同逻辑形态出现在多个变更块或文件中。→ 提取共享形态，两处共同调用。
- **依恋情结（Feature Envy）**：方法访问其他对象的数据多于自身数据。→ 把方法移到它依赖的数据上。
- **数据泥团（Data Clumps）**：相同的一组字段或参数总是一起传递，说明需要形成一种类型。→ 合并为一个类型并整体传递。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串代替应有自身类型的领域概念。→ 为概念创建小型类型。
- **重复 switch（Repeated Switches）**：针对相同类型的同一 `switch` 或 `if` 级联在变更中多次出现。→ 使用多态，或使用两处共享的一个映射。
- **霰弹式修改（Shotgun Surgery）**：一项逻辑变更迫使 diff 分散修改许多文件。→ 把共同变化的内容收拢到一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块因几个无关原因被修改。→ 拆分，使每个模块只因一种原因变化。
- **推测性通用（Speculative Generality）**：加入规格没有要求的抽象、参数或 hook。→ 删除并内联，直到出现真实需求。
- **消息链（Message Chains）**：调用方依赖很长的 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法隐藏遍历。
- **中间人（Middle Man）**：类或函数主要只是继续委派。→ 移除并直接调用真实目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现忽略或覆盖了大部分继承内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子 Agent

**标准子 Agent 的提示词**应包含：

- 完整 diff 命令和提交列表。
- 步骤 3 找到的标准文件列表，以及完整粘贴的代码气味基线（子 Agent 无法通过其他方式访问它）。
- 简报：“按相关文件或变更块报告：(a) diff 违反记录标准的所有位置，并引用标准（文件 + 规则）；(b) 发现的所有基线气味，注明名称并引用变更块。区分硬违规和判断：记录标准可以是硬要求，但基线气味始终属于判断，且仓库记录标准优先于基线。跳过工具已强制检查的内容。控制在 400 词以内。”

**规格子 Agent 的提示词**应包含：

- diff 命令和提交列表。
- 规格路径或获取到的正文。
- 简报：“报告：(a) 规格要求但缺失或只部分实现的内容；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现但实现方式可能错误的要求。每项发现引用规格行。控制在 400 词以内。”

缺少规格时，跳过规格子 Agent，并在最终报告中说明。

### 5. 汇总

把两份报告放在 `## Standards` 和 `## Spec` 标题下，可原样展示或轻微整理。**不要**合并发现或重新排序，因为两个轴有意保持独立（参见“为何使用两个轴”）。

结尾用一行总结：每个轴的发现总数及其各自最严重问题（如有）。不要在两个轴之间选一个“最严重问题”，那会重新引入本设计要避免的统一排序。

## 为何使用两个轴

一项变更可能通过一个轴却未通过另一个：

- 代码符合所有标准，却实现了错误功能 → **标准通过，规格失败。**
- 代码完全实现 issue 要求，却违反项目约定 → **规格通过，标准失败。**

分开报告可以避免一个轴掩盖另一个轴。
