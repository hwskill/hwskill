# 原型

原型是**用于回答一个问题、可以丢弃的代码**。问题决定原型的形态。

## 选择分支

根据用户提示、周边代码判断要回答的问题；如果用户在线，也可以询问：

- **“这个逻辑或状态模型合理吗？”** → 参阅 [LOGIC.md](LOGIC.md)。构建一个可分享的单文件 HTML，其中包含自由操作按钮和带标签页的引导式演练，用它推动状态机经历难以在纸面推理的情形，而且非开发者也能操作。
- **“它应该长什么样？”** → 参阅 [UI.md](UI.md)。在同一个路由上生成几种差异显著的 UI 方案，通过 URL 查询参数和底部悬浮栏切换。

两个分支会产出完全不同的制品，选错分支会浪费整个原型。如果问题确实有歧义且联系不上用户，选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这项假设。

## 两个分支共同适用的规则

1. **从第一天起就可丢弃，并清楚标明。**把原型代码放在接近实际使用位置的地方（紧邻它所验证的模块或页面），以便明确上下文；但名称要让普通读者一眼看出这是原型，而不是生产代码。对于可丢弃的 UI 路由，遵循项目现有路由约定，不要发明新的顶层结构。
2. **运行方式必须简单。**UI 原型通过项目任务运行器中的一条命令启动，例如 `pnpm <name>`、`python <path>` 或 `bun <path>`。逻辑演示则是用户可以双击打开的单个 HTML 文件。无论哪种方式，启动时都不应需要额外思考。
3. **默认不持久化。**状态保存在内存中。持久化是原型要验证的内容，而不是原型本身应依赖的条件。如果问题明确涉及数据库，使用临时数据库或名称清楚标为“PROTOTYPE, wipe me”的本地文件。
4. **省略打磨。**不写测试；除保证原型能运行所需的错误处理外，不补其他错误处理；不建立抽象。目标是快速获得答案。
5. **展示状态。**每次操作后（逻辑分支）或每次切换方案时（UI 分支），打印或渲染全部相关状态，让用户看到发生了什么变化。
6. **完成后保留证据。**把已经验证的决定纳入真实代码，然后把原型本身保存为**一手资料**：提交到从 main 分出的 `prototype/<name>` 临时分支，并在实现工单中留下指向该分支的上下文链接。还要在工单或提交中记录答案，即结论以及它解决的问题。主分支只保留经过验证的决定。
