# 分诊

让项目 issue 跟踪器中的 issue 在一组小型分诊角色状态机中流转。

如果该仓库把外部 Pull Request 视为请求入口（参见 issue 跟踪器配置），分诊也覆盖它们：**PR 是附带代码的 issue**，使用相同角色、状态和状态机；少量差异会在下文标为“对于 PR”。按照跟踪器配置，把单独的 `#42` 解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或 issue 都**必须**以此声明开头：

```
> *这是 AI 在分诊期间生成的内容。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写可长期使用的 Agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两种**类别**角色：

- `bug`：已有功能损坏
- `enhancement`：新功能或改进

五种**状态**角色：

- `needs-triage`：等待维护者评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：规格完整，可交给离线 Agent
- `ready-for-human`：需要人实施
- `wontfix`：不会处理

对于 PR，同样的状态应用于随附代码：`ready-for-agent` 表示已有简报，Agent 应对 diff 采取下一步；`ready-for-human` 表示可以由人合并。

每个已经分诊的 issue 应恰好带一个类别角色和一个状态角色。如果状态角色冲突，先标出问题并询问维护者，再执行其他操作。

这些是规范角色名。issue 跟踪器中实际使用的标签字符串可能不同，对应关系应已提供；如果没有，提示用户运行 `/setup-matt-pocock-skills`。

状态流转：没有标签的 issue 通常先进入 `needs-triage`，再转为 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖；遇到异常流转时先标出并询问。

## 调用方式

维护者调用 `/triage`，用自然语言说明意图。解释请求并执行。例如：

- “显示所有需要我关注的内容”
- “看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些内容可以交给 Agent？”

## 展示需要关注的内容

查询 issue 跟踪器并展示三组内容，每组从最早开始：

1. **无标签**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **`needs-info` 且报告者在最近分诊记录后有新活动**：需要重新评估。

PR 在范围内时，把外部 PR 加入这些组，并为每行标记 `[PR]` 或 `[issue]`。发现列表只显示**外部** PR（由跟踪器配置定义哪些作者属于外部），因此协作者正在处理的 PR 不属于分诊工作；该过滤只用于发现，明确点名的 PR 无论作者是谁都要分诊。

显示数量和每项的一行摘要，让维护者选择。

## 分诊特定 issue 或 PR

1. **收集上下文。**读取完整 issue 或 PR（正文、评论、标签、作者和日期；PR 还要读取 diff）。解析之前的分诊记录，避免重复询问已解决问题。使用项目领域词汇表探索代码库，并遵循所涉区域的 ADR。对代码库做两项检查：(a) **重复性**：按领域概念搜索请求行为是否已有实现，不要只按请求原话搜索，并报告检查位置。找到时属于“已实现”的 `wontfix`（步骤 5）。(b) **以前拒绝过**：读取 `.out-of-scope/*.md`，指出与本请求相似的内容。

2. **提出建议。**告诉维护者你建议的类别和状态及其理由，并简要概述与请求相关的代码库情况（包括是否已经实现）。等待指示。

3. **验证主张。**追问前先检查主张能否成立。对于 bug，根据报告者步骤复现；对于 PR，确认 diff 是否实现其声明：检出代码并运行相关测试或命令。报告结果：已确认（含代码路径）、验证失败，或信息不足（强烈指向 `needs-info`）。经确认的验证能产生更可靠的 Agent 简报。

4. **追问（如需要）。**请求需要补充时，使用 Skill 工具分别调用 `grilling` 和 `domain-modeling`，逐轮提问使其成形；决定形成时，明确领域术语，并立即更新 `CONTEXT.md` 或 ADR。

5. **应用结果：**
   - `ready-for-agent`：发布 Agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：使用与 Agent 简报相同的结构，但说明为何不能委派（判断、外部访问、设计决定或手工测试）。
   - `needs-info`：发布分诊记录（模板见下文）。
   - 对于 `wontfix`，关闭 issue，并根据**原因**选择评论：
     - **已经实现**：变更已存在于代码库中。指出具体位置；不要写入 `.out-of-scope/`（该知识库用于**被拒绝**的请求，而不是已构建功能）。
     - **拒绝（bug）**：礼貌解释后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接，然后关闭（参见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。有部分进展时可选择评论。

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，信任对方并直接应用角色。先确认将要执行的内容（角色变更、评论、关闭），然后行动。跳过追问。如果没有经过追问就移至 `ready-for-agent`，询问是否需要编写 Agent 简报。

## Needs-info 模板

```markdown
## 分诊记录

**目前已经确定：**

- 要点 1
- 要点 2

**仍需要你提供（@reporter）：**

- 问题 1
- 问题 2
```

把追问中已经确定的所有内容写入“目前已经确定”，避免工作丢失。问题必须具体、可执行，不能只写“请提供更多信息”。

## 恢复以前的会话

如果 issue 或 PR 中已有分诊记录，先读取并检查报告者是否回答了待解决问题；展示最新情况后再继续。不要重复询问已经解决的问题。
