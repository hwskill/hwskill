# 诊断缺陷

这是一套用于困难缺陷的纪律。只有明确说明理由时才可跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在），建立对相关模块的清晰心智模型，并检查所涉区域的 ADR。

## 脱敏

本技能会展示命令、输出和采集制品。**先对所有秘密脱敏**：用 `<REDACTED>` 替换。让循环通过环境变量使用凭据，使凭据留在环境中而不是出现在展示内容里。采集制品可能带认证头，只引用携带有效信号的行。

如果脱敏后的输出不足以诊断缺陷，明确说明并询问用户。

## 阶段 1：建立反馈循环

**这就是本技能的核心。**其余部分都是机械步骤。如果有一个针对该缺陷的**紧密**通过/失败信号（能在**这个**缺陷上变红），你就能找到原因；二分、假设检验和插桩都只是使用该信号。没有信号时，无论盯着代码多久都无济于事。

在这里投入远高于其他阶段的精力。**积极、灵活，不轻易放弃。**

### 建立反馈循环的方法，大致按此顺序

1. 在能到达缺陷的接缝处编写**失败测试**：单元、集成或端到端。
2. 针对运行中的开发服务器编写 **curl/HTTP 脚本**。
3. 使用固定输入调用 **CLI**，把标准输出与已知正确快照比较。
4. 编写**无头浏览器脚本**（Playwright/Puppeteer）驱动 UI，并对 DOM、控制台或网络进行断言。
5. **重放采集的 trace。**把真实网络请求、载荷或事件日志保存到磁盘，通过隔离的代码路径重放。
6. **临时测试台。**启动系统的最小子集（一个服务、mock 依赖），用一次函数调用执行缺陷路径。
7. **属性或模糊测试循环。**如果缺陷表现为“输出偶尔错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分测试台。**如果缺陷出现在两个已知状态之间（提交、数据集或版本），自动执行“在状态 X 启动、检查、重复”，从而运行 `git bisect run`。
9. **差分循环。**让相同输入分别通过旧版本和新版本（或两个配置），比较输出。
10. **人在回路中的 Bash 脚本。**最后手段。如果必须由人点击，使用 `scripts/hitl-loop.template.sh` 驱动人的步骤，使循环仍然结构化。采集输出会返回给你。

建立正确的反馈循环后，缺陷已经解决了 90%。

### 收紧循环

把循环当作产品。拥有一个循环后继续**收紧**：

- 能否更快？（缓存设置、跳过无关初始化、缩小测试范围。）
- 信号能否更明确？（对具体症状断言，而不是只检查“没有崩溃”。）
- 能否更确定？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环只比没有循环稍好；耗时 2 秒且确定的循环才称得上紧密，是调试中的强大工具。

### 非确定性缺陷

目标不是得到干净复现，而是提高**复现率**。循环触发 100 次、并行运行、增加压力、缩小时间窗口、注入 sleep。50% 概率的缺陷可以调试，1% 的缺陷很难调试；继续提高复现率，直至足以调试。

### 确实无法建立循环时

停止并明确说明。列出已经尝试的内容。向用户请求：(a) 可复现问题的环境访问权，(b) 已脱敏的采集制品（HAR 文件、日志转储、core dump、带时间戳的屏幕录像），或 (c) 增加临时生产插桩的许可。**不要**在没有循环时继续提出假设。

### 完成条件：一个能够变红的紧密循环

阶段 1 在循环既**紧密**又**能变红**时完成：你能给出**一条命令**（脚本路径、测试调用或 curl），而且已经**至少运行一次**并展示调用和脱敏输出；同时满足：

- [ ] **能变红**：它驱动真实缺陷路径并断言**用户描述的准确症状**，因此能在该缺陷存在时变红、修复后变绿。不能只检查“运行时没有报错”，必须能捕获这个具体缺陷。
- [ ] **确定**：每次运行得到相同结论（不稳定缺陷按上文固定为较高复现率）。
- [ ] **快速**：用时为秒，而不是分钟。
- [ ] **Agent 可运行**：可以无人值守运行；只有通过 `scripts/hitl-loop.template.sh` 才允许人在回路中。

如果在这条命令存在前就开始读代码建立理论，**立即停止：直接跳到假设正是本技能要防止的失败。**没有能变红的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环，观察缺陷出现时它变红。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好发生在附近的另一个失败。错误的缺陷会得到错误的修复。
- [ ] 多次运行都可复现；对于非确定性缺陷，复现率足够高，可以用于调试。
- [ ] 已捕获准确症状（错误消息、错误输出或缓慢耗时），后续阶段可以据此确认修复确实解决问题。

### 最小化

循环变红后，把复现缩小到**仍然变红的最小场景**。每次只删除一项输入、调用方、配置、数据或步骤，随后重新运行循环；只保留对失败不可缺少的内容。

原因：最小复现会缩小阶段 3 的假设空间（剩余可疑活动部件更少），并成为阶段 5 中干净的回归测试。

完成条件是**每个剩余元素都不可缺少**：去掉任何一个都会让循环变绿。

在完成复现和最小化前不要继续。

## 阶段 3：提出假设

测试任何假设前，先生成 **3–5 个有排序的假设**。只提出一个假设会让思路锚定在第一个看似合理的解释上。

每个假设都必须**可证伪**：说明它会作出什么预测。

> 格式：“如果 <X> 是原因，那么改变 <Y> 会让缺陷消失，或改变 <Z> 会让它更严重。”

无法说明预测时，这只是模糊感觉；丢弃或把它明确化。

**测试前向用户展示排序列表。**用户可能掌握能立即改变排序的领域知识（“我们刚部署了与第 3 项相关的变更”），或知道哪些假设已经排除。这是成本低、收益大的检查点。不要因此阻塞；用户离线时按你的排序继续。

## 阶段 4：插桩

每个探针都必须对应阶段 3 的一个具体预测。**一次只改变一个变量。**

工具优先级：

1. 环境支持时使用**调试器或 REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界添加**定向日志**。
3. 绝不“把一切写入日志再 grep”。

**给每条调试日志增加唯一前缀**，例如 `[DEBUG-a4f2]`。结束时只需一次 grep 即可清理。没有标签的日志容易残留；带标签的日志必须删除。

**性能分支。**性能回归通常不适合使用日志。应先建立基线测量（计时测试台、`performance.now()`、分析器、查询计划），然后二分。先测量，再修复。

## 阶段 5：修复和回归测试

在修复前编写回归测试，但前提是存在**正确的接缝**。

正确接缝能按真实调用位置出现的方式执行**实际缺陷模式**。如果唯一可用接缝太浅（缺陷需要多个调用方，却只能做单调用方测试；单元测试无法复现触发缺陷的调用链），在那里写回归测试会带来错误信心。

**没有正确接缝本身就是发现。**记录它：代码库架构阻止了对缺陷的可靠锁定，并在下一阶段明确标出。

如果存在正确接缝：

1. 把最小复现转换为该接缝处的失败测试。
2. 观察测试失败。
3. 应用修复。
4. 观察测试通过。
5. 针对原始、未最小化的场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理

声明完成前必须做到：

- [ ] 原始复现不再出现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已经记录缺少接缝）
- [ ] 删除全部 `[DEBUG-...]` 插桩（grep 该前缀）
- [ ] 删除临时原型（或移至清楚标记的调试位置）
- [ ] 在提交或 PR 消息中说明最终正确的假设，让下一位调试者能够复用结论
