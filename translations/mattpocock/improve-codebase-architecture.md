# 改善代码库架构

找出架构摩擦并提出**加深机会**：把浅模块重构为深模块。目标是提高可测试性和 Agent 可导航性。

本命令以项目领域模型为依据，并建立在共享设计词汇上：

- 使用 Skill 工具调用 `codebase-design`，取得架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、“接口就是测试面”、“一个适配器代表假设接缝，两个才是真实接缝”）。每条建议都要准确使用这些术语，不要漂移为“组件”“服务”“API”或“边界”。
- `CONTEXT.md` 中的领域语言为良好接缝命名；`docs/adr/` 中的 ADR 记录本命令不应重新争论的决定。

## 流程

### 1. 探索

**扫描前先限定范围：YAGNI。**加深模块的收益在于使未来变更更容易，因此要更重视近期频繁变化的代码区域。查看代码前先决定**查看哪里**：

- 如果用户指定了方向（模块、子系统或痛点），直接采用并跳过下面的推断。
- 否则，向前查看足够长的一段提交历史（`git log --oneline`），找出代码库热点，即反复出现的文件和区域，并优先关注这些路径。如果变更分散、没有明确热点，再扩大范围。

先阅读项目领域词汇表（`CONTEXT.md`）以及所涉区域的 ADR。

然后派一个子 Agent 浏览代码库。不要机械套用启发式规则；自然探索并记录遇到摩擦的位置：

- 理解一个概念是否需要在许多小模块之间来回跳转？
- 哪些模块很**浅**，接口几乎和实现一样复杂？
- 哪些纯函数只是为了可测试性而抽出，但真实缺陷藏在调用方式中，缺少**局部性**？
- 哪些紧耦合模块会跨接缝泄漏？
- 代码库哪些部分没有测试，或难以通过当前接口测试？

对任何疑似浅模块应用**删除测试**：删除它会集中复杂性，还是只会搬动复杂性？你需要的是“会集中复杂性”的信号。

### 2. 用 HTML 报告展示候选项

把自包含 HTML 文件写入操作系统临时目录，避免文件进入仓库。临时目录优先取 `$TMPDIR`，否则用 `/tmp`（Windows 使用 `%TEMP%`）；文件名为 `<tmpdir>/architecture-review-<timestamp>.html`，保证每次运行生成新文件。为用户打开文件（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告知绝对路径。

报告使用 CDN 版 **Tailwind** 完成布局和样式，在图、流程或时序能可靠表达结构时使用 CDN 版 **Mermaid**。Mermaid 与手写 CSS/SVG 视觉可以混用：关系呈图状时（调用图、依赖、时序）使用 Mermaid；需要更具编辑设计感的效果（质量图、剖面图、折叠动画）时使用手工 div/SVG。每个候选项都要有**前后对比可视化**，整体要重视视觉表达。

每个候选项用一张卡片呈现：

- **文件**：涉及哪些文件或模块
- **问题**：当前架构为何造成摩擦
- **方案**：用通俗语言说明会改变什么
- **收益**：从局部性、杠杆及测试改善角度解释
- **前后对比图**：并排自绘，表现当前的浅度以及加深后的变化
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三者之一，以徽章展示

报告结尾增加**首要推荐**，说明应优先处理哪个候选项以及理由。

**领域使用 CONTEXT.md 的词汇，架构使用 `/codebase-design` 的词汇。**如果 `CONTEXT.md` 定义了 “Order”，应说“Order intake 模块”，不要说 “FooBarHandler” 或 “Order 服务”。

**ADR 冲突**：候选项与现有 ADR 冲突时，只有摩擦严重到值得重新审视 ADR 才提出，并在卡片中明确标注，例如警告：“与 ADR-0007 冲突，但值得重开讨论，因为……”。不要列出 ADR 禁止的每一种理论性重构。

完整 HTML 骨架、图表模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提出接口。文件写好后询问用户：“你想深入探索哪一项？”

### 3. 追问循环

用户选择候选项后，使用 Skill 工具调用 `grilling`，与用户一起遍历决策树：约束、依赖、加深后模块的形态、接缝后隐藏的内容以及能保留下来的测试。

决定形成时立即产生相应副作用；使用 Skill 工具调用 `domain-modeling`，在过程中保持领域模型最新：

- **加深后的模块以 `CONTEXT.md` 中尚不存在的概念命名？**把术语加入 `CONTEXT.md`。如果文件不存在，按需创建。
- **对话中明确了模糊术语？**立即更新 `CONTEXT.md`。
- **用户因关键理由拒绝候选项？**提议 ADR：“要不要把这项理由记为 ADR，避免未来架构评审重复建议？”只有未来探索者确实需要该理由才能避免重复建议时才提出；“现在不值得”等短期理由或不言自明的理由无需记录。
- **希望探索加深后模块的替代接口？**使用 Skill 工具调用 `codebase-design`，采用其中“设计两次”的并行子 Agent 模式。
