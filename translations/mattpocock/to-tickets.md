# 转换为工单

把计划、规格或对话拆成一组**工单**：每张都是曳光弹式纵向切片，并声明会**阻塞**它的其他工单。

issue 跟踪器和分诊标签词汇应已提供。如果没有，提示用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

使用对话中已有的上下文。如果用户通过参数传入引用（规格路径、issue 编号或 URL），获取并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果尚未探索代码库，就先了解代码现状。工单标题和描述应使用项目领域词汇表中的词汇，并遵循所涉区域的 ADR。

寻找预先重构代码以降低实现难度的机会：“先让变更变得容易，再完成容易的变更。”

### 3. 起草纵向切片

把工作拆成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片要狭窄但完整地贯穿所有层（schema、API、UI、测试）：它是纵向切片，不是单个层的横向切片
- 完成后的切片可以独立演示或验证
- 每个切片的规模应能放进一个全新的上下文窗口
- 预先重构应最先完成

</vertical-slice-rules>

为每张工单指定**阻塞边**，即开始前必须完成的其他工单。没有阻塞项的工单可以立即开始。

**广域重构是纵向切片的例外。****广域重构**是一项机械变更（重命名列、修改共享符号类型），其**影响半径**会扩散到整个代码库，使一次修改同时破坏成千上万个调用点，因而任何纵向切片都无法以绿色状态落地。不要强行把它做成曳光弹，应按**扩展—收缩**排序。先扩展：在旧形式旁增加新形式，保持一切可用。随后按影响半径分批迁移调用点（按包或目录），每批一张工单，并被扩展工单阻塞；旧形式仍存在，因此每批之间 CI 保持绿色。最后收缩：所有调用方迁移后删除旧形式，该工单被所有迁移批次阻塞。即便单个批次也无法独立保持绿色时，仍保留这个序列，但让各批次共享一个集成分支，并全部阻塞最终的集成验证工单；只承诺在那里恢复绿色。

### 4. 向用户确认

把建议拆分显示为编号列表。每张工单包括：

- **标题**：简短的描述性名称
- **被哪些项阻塞**：开始前必须完成的其他工单（如有）
- **交付内容**：该工单会让哪项端到端行为可用

询问用户：

- 粒度是否合适（太粗或太细）？
- 阻塞边是否正确：每张工单是否只依赖真正阻止它开始的工单？
- 是否需要合并或进一步拆分工单？

迭代到用户批准拆分。

### 5. 发布到已配置的跟踪器

发布获批工单。具体方式取决于 `/setup-matt-pocock-skills` 配置的跟踪器；工单内容相同，只有阻塞边的表示形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写一个文件，按依赖顺序从 `01` 编号（阻塞项在前）。每个文件的“Blocked by”列出它依赖的编号和标题。使用下方单工单文件模板：每张工单一个文件，绝不合并成单个文件。
- **真实 issue 跟踪器（GitHub、Linear 等）** → 按依赖顺序逐张发布 issue（阻塞项在前），使每条阻塞边能引用真实标识。平台支持原生 blocking 或 sub-issue 关系时使用原生关系；否则在每张工单的 “Blocked by” 中写入阻塞 issue。除非另有指示，应用 `ready-for-agent` 分诊标签；这些工单按设计即可由 Agent 领取。

按**前沿**工作：任何阻塞项均已完成的工单都在前沿。纯线性链就是从上到下执行。

不要关闭或修改父 issue。
