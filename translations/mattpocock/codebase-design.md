# 代码库设计

设计**深模块**：在干净接缝处，以小接口隐藏大量行为，并能通过该接口测试。凡是设计或重构代码，都使用这里的语言和原则。目标是让调用方获得杠杆，让维护者获得局部性，并让所有人获得可测试性。

## 词汇表

准确使用这些术语，不要替换成“组件”“服务”“API”或“边界”。统一语言本身就是目标。

**模块（Module）**：任何具有接口和实现的事物。它有意不限定规模，可以是函数、类、包或跨层切片。应避免：单元、组件、服务。

**接口（Interface）**：调用方正确使用模块必须知道的一切，包括类型签名，以及不变量、顺序约束、错误模式、必需配置和性能特征。应避免：API、签名（范围过窄，只表示类型层面的表面）。

**实现（Implementation）**：模块内部的代码主体。它不同于**适配器**：某个事物可以是小适配器但具有大型实现（Postgres 仓库），也可以是大适配器但实现很小（内存 fake）。讨论接缝时使用“适配器”，其他情况使用“实现”。

**深度（Depth）**：接口提供的杠杆，即调用方（或测试）每学习一单位接口可以执行多少行为。小接口后隐藏大量行为的模块是**深**模块；接口几乎与实现同样复杂的模块是**浅**模块。

**接缝（Seam）**（Michael Feathers）：无需在某处直接编辑就能改变行为的位置；也就是模块接口所在的**位置**。接缝放在哪里是独立设计决定，与接缝后面放什么不同。应避免：“边界”（会与 DDD 的 bounded context 混淆）。

**适配器（Adapter）**：在接缝处满足接口的具体事物。它描述的是**角色**（填入哪个位置），而不是材料（内部是什么）。

**杠杆（Leverage）**：调用方从深度获得的收益。每学习一单位接口，就获得更多能力。一份实现可以服务 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度获得的收益。变更、缺陷、知识和验证集中在一个位置，而不扩散到调用方。一处修复，处处生效。

## 深模块与浅模块

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口         │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│       深实现         │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│             大接口               │  ← 方法多、参数复杂
├─────────────────────────────────┤
│             薄实现               │  ← 只是传递调用
└─────────────────────────────────┘
```

设计接口时询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂性？

## 原则

- **深度是接口的属性，而不是实现的属性。**深模块内部仍可由可 mock、可替换的小部件组合而成；只是它们不属于接口。模块既可以有实现私有、供自身测试使用的**内部接缝**，也有位于接口处的**外部接缝**。
- **删除测试。**想象删除该模块。如果复杂性随之消失，它只是传递层；如果复杂性重新出现在 N 个调用方中，它就发挥了价值。
- **接口就是测试面。**调用方和测试跨越相同接缝。如果希望越过接口深入测试，模块形态很可能有问题。
- **一个适配器代表假设接缝，两个适配器才代表真实接缝。**除非接缝两侧确有变化，否则不要引入接缝。

## 为可测试性而设计

良好接口使测试自然发生：

1. **接收依赖，不要自行创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要直接产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **较小的表面积。**方法越少，需要的测试越少；参数越少，测试设置越简单。

## 关系

- 一个**模块**恰好有一个**接口**，即向调用方和测试展示的表面。
- **深度**是**模块**相对于其**接口**的属性。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**上并满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 不采用的表述

- **以实现代码行数与接口代码行数之比定义深度**（Ousterhout）：这会奖励填充实现。这里采用“深度即杠杆”。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：范围太窄；这里的接口包含调用方必须知道的每项事实。
- **“边界”**：容易与 DDD 的 bounded context 混淆。应使用**接缝**或**接口**。
