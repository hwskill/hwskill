# 领域建模

在设计过程中主动建立并完善项目的领域模型。这是一项**主动**实践：质疑术语、构造边界场景，并在词汇和决定一旦明确时立即写入词汇表和决策记录。（仅仅为了使用词汇而**读取** `CONTEXT.md` 不属于本技能；任何技能都能把它作为一行习惯。本技能用于改变模型，而不仅是使用模型。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，仓库包含多个上下文。该映射会指出每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 特定上下文的决定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件：只有有内容可写时才创建。不存在 `CONTEXT.md` 时，在第一个术语得到确定后创建；不存在 `docs/adr/` 时，在需要第一份 ADR 时创建。

## 会话期间

### 对照词汇表提出质疑

用户使用的术语与 `CONTEXT.md` 中既有语言冲突时，立即指出：“你的词汇表把‘取消’定义为 X，但你现在似乎指 Y。应该是哪一个？”

### 明确模糊语言

用户使用含糊或一词多义的术语时，提出精确的规范术语：“你说的‘账户’是 Customer 还是 User？它们是不同概念。”

### 讨论具体场景

讨论领域关系时，用具体场景进行压力测试。构造能探查边界情况的场景，促使用户精确定义概念之间的边界。

### 与代码交叉核对

用户说明某项机制时，检查代码是否一致。发现矛盾时明确提出：“代码会取消整个 Order，但你刚才说可以部分取消。哪一个才是正确行为？”

### 立即更新 CONTEXT.md

术语一旦确定，就立即更新 `CONTEXT.md`。不要攒到最后批量处理；应在决定发生时记录。格式参见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 必须完全不含实现细节。不要把它当作规格、草稿区或实现决定仓库。它只是一份词汇表。

### 谨慎提议 ADR

只有以下三项同时成立时才提议创建 ADR：

1. **难以撤销**：以后改变决定的成本显著
2. **脱离上下文会令人意外**：未来读者会问“他们为什么这样做？”
3. **来自真实取舍**：存在真正的替代方案，并因具体理由选择了其中一个

缺少任何一项都不写 ADR。格式参见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
