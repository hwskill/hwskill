# 测试驱动开发

TDD 是红 → 绿循环。本技能是一份参考，使这个循环产出值得保留的测试：什么是好测试、测试应该放在哪里、有哪些反模式，以及循环的规则。每一节都适用于每一轮循环；应在循环开始前和进行中查阅，而不是事后再看。

探索代码库时，读取 `CONTEXT.md`（如果存在），使测试名称和接口词汇与项目领域语言一致，并遵循所改区域中的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变，测试不应随之失效。好测试读起来像规格：“用户可以用有效购物车结账”准确说明了现有能力，而且重构后仍然成立，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝（seam）**是被测试的公共边界：你可以通过该接口观察行为，而无需探入内部。测试位于接缝处，绝不针对内部实现。

**只在预先商定的接缝处测试。**编写任何测试前，先写出要测试的接缝并与用户确认。未经确认的接缝不能写测试。你不可能测试一切，因此预先约定接缝能让测试投入落在关键路径和复杂逻辑上，而不是每个边界情况。

询问：“公共接口是什么？我们应该测试哪些接缝？”

当接口本身的形态仍有疑问（模块应有多深、接缝应放在哪里、接口应暴露什么），使用 Skill 工具调用 `codebase-design` 获取词汇。它是模块、接口、深度、接缝、适配器、杠杆和局部性等术语的共享来源，是供查阅的参考，不是需要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（例如查询数据库而不是使用接口）。识别信号是：行为没有变化，重构却让测试失败。
- **同义反复**：断言用与代码相同的方法重新计算期望值（如 `expect(add(a, b)).toBe(a + b)`、用同样方法手工生成快照，或断言常量等于自身），因此测试必然通过，不可能与代码产生分歧。期望值必须来自独立事实来源：已知正确的字面值、完整推导的示例或规格。
- **横向切片**：先写完全部测试，再写全部实现。批量测试验证的是**想象中的**行为：你测试的是事物的形状，而不是面向用户的行为；测试对真实变化不敏感，而且在理解实现之前就锁定了测试结构。应改用**纵向切片**：一个测试 → 一个实现 → 重复；每个测试都是一颗**曳光弹**，根据上一轮学到的内容继续前进。

## 循环规则

- **先红后绿。**先写失败测试，然后只写足以让它通过的代码。不要预判后续测试，也不要添加推测性功能。
- **一次一个切片。**每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于这个循环。**它属于评审阶段（参见 `code-review` 技能），而不是红 → 绿实现循环。
