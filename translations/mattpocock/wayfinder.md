一个松散想法出现了：规模超过一次 Agent 会话，且笼罩在迷雾中，从当前位置到**目的地**的路径尚不可见。寻路的重点是找到这条路，而不是直接冲向目的地。本技能会在仓库 issue 跟踪器上把道路绘制为**共享地图**，然后逐项处理其中的**决策工单**（解决后得到决定的问题，而不是要执行的构建切片），直到路线清晰。

每项工作的目的地不同，为它命名是绘图的第一步，因为它会塑造每张工单。目的地可能是一份待交接和迭代的规格、规划开始前必须确定的决定，或在原处完成的变更，例如数据结构迁移。地图与领域无关：工程工作、课程内容或任何符合这种形态的事项都可使用。

## 规划，不执行

Wayfinder 默认用于**规划**：每张工单解决一项决定；当道路清晰、执行前不再有未决事项时，地图完成。想直接开始做事的冲动通常说明已经到达地图边缘，应该交接。工作可以在**备注**中覆盖默认规则，把执行本身纳入地图；如果没有覆盖，就应产出决定，而不是交付物。

## 使用名称引用

每张地图和工单都是 issue，因此都有一个**名称**，即标题。在人阅读的所有内容（过程说明、地图的“已有决定”）中，都按名称引用，绝不只写 id、编号或 slug。由 `#42、#43、#44` 组成的墙无法阅读，名称则一眼可辨。id 和 URL 仍然存在，由名称包装成链接；它们位于名称**内部**，不能替代名称。

## 地图

地图是该仓库 issue 跟踪器上的单个 issue，带 `wayfinder:map` 标签，是规范制品。地图的工单是其子 issue。

地图是**索引**，不是存储库。它列出已经作出的决定，并指向保存细节的工单；一项决定只存在于一个地方，即其工单，因此地图绝不重新陈述，只提供摘要和链接。

**地图、子工单、阻塞关系和前沿查询的物理表示由跟踪器决定。**issue 跟踪器信息应已提供；如果没有，提示用户运行 `/setup-matt-pocock-skills`。查看跟踪器文档中的“Wayfinding operations”，了解**当前**仓库如何表达这些操作。没有跟踪器信息时，默认使用本地 Markdown 跟踪器。

### 工单

每张工单都是地图的**子 issue**，以跟踪器 issue id 作为身份。正文是需要回答的问题，规模应能放入一次 10 万 token 的 Agent 会话：

```markdown
## 问题

<本工单要解决的决定或调查>
```

每张工单带一种 `wayfinder:<type>` 标签：`research`、`prototype`、`grilling` 或 `task`（参见[工单类型](#工单类型)）。

会话开始任何工作前，先把工单分配给推动地图的开发者，以此**领取**工单，使并发会话能够跳过。该 assignee 就是领取标记：开放且没有 assignee 的工单尚未领取。

阻塞关系使用跟踪器的**原生**依赖关系。这一点很关键，因为它会在跟踪器 UI 中直观呈现前沿，人无需打开地图就能看到哪些工单可领取。只有不支持原生阻塞的跟踪器才退回到正文约定。阻塞一张工单的所有工单均关闭后，该工单即为**未阻塞**；所有开放、未阻塞、未领取的子工单组成**前沿**，也就是已知地图的边缘。

答案不属于正文，而是在解决时记录（参见[逐项处理地图](#逐项处理地图)）。解决工单时创建的制品应从 issue 链接，而不是粘贴进去。

## 工单类型

每张工单要么是 **HITL**（人在回路中，与亲自表达观点的人共同处理），要么是 **AFK**（Agent 独立处理）。HITL 工单只能通过现场交流解决；Agent 绝不能代替人回答其一方的问题（自己回答追问的 Agent 已经破坏流程）。

- **调研（Research，AFK）**：阅读文档、第三方 API 或知识库等本地资源，找出某项决定依赖的事实。由调用 Skill 工具中 `research` 的子 Agent 解决。需要当前工作目录之外的知识时使用。
- **原型（Prototype，HITL）**：使用 Skill 工具调用 `prototype`，制作便宜、粗糙、具体的制品（大纲、粗稿、桩代码或 UI/逻辑代码），提高讨论保真度，使用户能够作出反应。把原型链接为制品。关键问题是“应该长什么样”或“应该怎样运行”时使用。
- **追问（Grilling，HITL）**：对话，默认类型。始终使用 Skill 工具分别调用 `grilling` 和 `domain-modeling`。
- **任务（Task，HITL 或 AFK）**：作出一项**决定**前必须完成的手工工作；没有要决定、原型化或调研的内容，但讨论在工作完成前被阻塞。例如注册服务以评估 API、配置访问、移动数据以查看其形态。这是唯一会**执行**而非决定的类型；其价值是解除决定的阻塞，而不是交付目的地。Agent 能做时独立执行（AFK），否则向人提供精确清单（HITL）。工作完成时解决；答案记录做了什么以及后续工单依赖的事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图有意保持不完整：看不清的部分不要绘制。现有工单之外是**战争迷雾**：你能隐约看见即将出现的决定和调查，却因它们依赖仍开放的问题而无法精确定义。每解决一张工单，前方迷雾就会消散；现在能明确的内容逐个升级为新工单，直到通往目的地的道路清晰且没有工单剩余。

地图的**尚未明确**一节用于记录这种模糊视图：怀疑存在的问题、以后需要回看的区域。它是朝向目的地的尚未发现前沿：其中所有内容都在范围内，只是还不够清晰，不能成为工单。可以按当前可见程度宽泛或完整地记录；它也为协作者说明工作前进方向。

**迷雾还是工单？**判断标准是现在能否准确陈述问题，而不是现在能否回答。

- **成为工单**：问题已经清晰，即使仍被阻塞、目前无法行动。
- **保持尚未明确**：还无法清楚表述。不要把迷雾预切成工单大小；它比工单粗糙，一个区域在前沿到达后可能升级为多张工单，也可能一个都不需要。

**尚未明确**不包含已经决定的内容（已有决定）、现有工单或范围外内容（下一节）。

## 范围外

迷雾只会朝**目的地**聚集。目的地确定范围，因此目的地之外的工作属于**范围外**：它不是迷雾，也不应放入**尚未明确**。它在地图中有独立的**范围外**一节，保存你有意识排除在**本次**工作之外的内容。决定它属于这里的是范围，而不是清晰程度。

范围外工作永远不会升级为工单（前沿在目的地停止）。只有重新定义目的地时才会再次出现，并作为全新工作，而不是恢复旧工作。

判定某项内容超出范围是限定范围的动作，而不是路线中的一步。如果一张已有工单后来发现位于目的地之外（绘图时误纳入，或解决其他问题后才暴露），就**关闭它**（关闭工单明确不在前沿），并在**范围外**一节留一行：摘要、超出范围的原因，以及指向已关闭工单的链接。不要放入**已有决定**，后者记录实际走过的路线；范围边界不是路线中的一步。

## 调用方式

有两种模式。无论哪种，除调研工单外，**一次会话绝不解决超过一张工单**。

### 绘制地图

用户带着模糊想法调用。

1. **命名目的地。**使用 Skill 工具分别调用 `grilling` 和 `domain-modeling`，确定地图要通往的规格、决定或变更。目的地确定范围，因此最先决定。
2. **绘制前沿。**再次追问，这次采用**广度优先**：横跨整个空间展开，而不是深入单条线索，找出开放决定和现在可以采取的第一步。**如果没有发现迷雾**（通往目的地的道路已经清晰，整个旅程小到一次会话能容纳），就不需要地图。停止并询问用户希望如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填写目的地和备注，已有决定留空，把迷雾概括在**尚未明确**。
4. 把现在能明确的工单创建为地图的子 issue，然后在**第二轮**连接阻塞边（issue 需要先获得 id 才能互相引用）。连接后，工单分为前沿和阻塞项；尚无法明确的内容继续留在**尚未明确**。
5. **启动调研子 Agent。**为刚创建的每张 `research` 工单启动调用 Skill 工具中 `research` 的子 Agent，并行解决；结果保存在临时 `research/<name>` 分支，工单中保留上下文链接。
6. 停止：绘图就是一次会话的工作，不在此会话手工解决工单。

### 逐项处理地图

用户用地图 URL 或编号调用。工单参数**可选**：没有指定时，由你选择下一项决定，而不是让用户选择。

1. 加载**地图**：只加载低分辨率视图，不读取每张工单正文。
2. 选择工单。用户指定时采用指定项，否则按顺序取第一张前沿工单。先**领取**：任何工作前把它分配给自己。
3. 解决工单。按需**放大**：需要时获取任何相关或已关闭工单的完整正文；调用 `## 备注` 指定的技能。不确定时，使用 Skill 工具分别调用 `grilling` 和 `domain-modeling`。
4. 记录结果：把答案作为**解决评论**发布，**关闭** issue，并在地图的“已有决定”中追加上下文链接。
5. 添加新发现的工单（先创建再连接）；把答案已经变得可明确的迷雾升级为工单，并从**尚未明确**删除相应区域，使其只存在于新工单中。如果答案表明某张工单（当前或其他）位于目的地之外，应**判定为范围外**，而不是把它当作路线决定解决。如果该决定使地图其他部分失效，更新或删除相关工单。

用户可能并行处理未阻塞工单，因此要预期其他会话同时编辑跟踪器。
