# 系统化调试

## 概述

**核心原则：**尝试修复前，始终先找到根因。只修症状就是失败。

**违反此流程的字面要求，也就是违反调试的精神。**

## 铁律

```
没有先调查根因，就不能修复
```

如果尚未完成第一阶段，就不能提出修复方案。

## 使用时机

用于**任何**技术问题：

- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要使用：**

- 面临时间压力（紧急情况容易诱使人猜测）
- “只做一个快速修复”看起来很明显
- 已经尝试多种修复
- 上一次修复没有奏效
- 你尚未完全理解问题

**以下情况也不要跳过：**

- 问题看起来很简单（简单 bug 也有根因）
- 你很赶时间（匆忙必然导致返工）
- 经理要求“现在就修好”（系统方法比反复试错更快）

## 四个阶段

进入下一阶段前，必须完成当前阶段。

### 第一阶段：调查根因

**尝试任何修复之前：**

1. **认真阅读错误消息**
   - 不要跳过错误或警告
   - 它们往往包含准确解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径和错误码

2. **稳定复现**
   - 能否可靠触发？
   - 准确步骤是什么？
   - 每次都会发生吗？
   - 无法复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 哪些变更可能导致此问题？
   - 查看 Git diff 和近期提交
   - 新依赖、配置变化
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件（CI → 构建 → 签名，API → 服务 → 数据库）时：**

   **提出修复前，增加诊断观测：**

   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境和配置是否正确传递
     - 检查每一层的状态

   运行一次，收集能显示故障位置的证据
   然后分析证据，识别失败组件
   再调查该特定组件
   ```

   **示例（多层系统）：**

   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：**哪一层失败（secret → workflow ✓，workflow → build ✗）。

5. **追踪数据流**

   **当错误位于调用栈深处时：**

   阅读本目录的 `root-cause-tracing.md`，了解完整的反向追踪方法。

   **简要版本：**

   - 错误值来自哪里？
   - 谁用这个错误值调用了当前函数？
   - 持续向上追踪，直到找到来源
   - 在来源处修复，而不是在症状处修补

### 第二阶段：模式分析

**修复前先找到模式：**

1. **寻找可用示例**
   - 在同一代码库中找到相似且正常工作的代码
   - 哪些与损坏部分相似的内容能够工作？

2. **对照参考实现**
   - 如果在实现某种模式，完整阅读参考实现
   - 不要略读——逐行阅读
   - 完全理解模式后再应用

3. **识别差异**
   - 正常与损坏实现之间有什么不同？
   - 列出所有差异，无论多小
   - 不要假设“这不可能有影响”

4. **理解依赖**
   - 它还需要哪些组件？
   - 需要什么设置、配置和环境？
   - 它作出了哪些假设？

### 第三阶段：假设与测试

**采用科学方法：**

1. **形成单一假设**
   - 明确陈述：“我认为 X 是根因，因为 Y”
   - 写下来
   - 具体，不要模糊

2. **最小化测试**
   - 只做验证假设所需的最小变更
   - 一次只改一个变量
   - 不要同时修复多个问题

3. **继续前验证**
   - 奏效？是 → 第四阶段
   - 没奏效？形成新的假设
   - 不要在旧修复上叠加更多修复

4. **不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 寻求帮助
   - 继续调研

### 第四阶段：实现

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 能自动化就写自动测试
   - 没有框架时写一次性测试脚本
   - 修复前必须存在
   - 使用 `superpowers:test-driven-development` 编写合适的失败测试

2. **实施单一修复**
   - 解决已识别的根因
   - 一次只做一个变更
   - 不做“顺手改进”
   - 不捆绑重构

3. **验证修复**
   - 测试现在通过吗？
   - 其他测试是否仍正常？
   - 问题真的解决了吗？
   - 声称成功前使用 `superpowers:verification-before-completion`

4. **修复无效时**
   - 停止
   - 统计尝试过多少次修复
   - 少于 3 次：回到第一阶段，结合新信息重新分析
   - **达到 3 次：停止并质疑架构（见下方第 5 项）**
   - 未进行架构讨论前，不要尝试第 4 次修复

5. **3 次以上修复失败：质疑架构**

   **表明架构有问题的模式：**

   - 每次修复都在不同位置暴露新的共享状态、耦合或问题
   - 修复需要“大规模重构”
   - 每项修复都在其他地方制造新症状

   **停止并质疑基础：**

   - 该模式从根本上合理吗？
   - 是否只是“因为惯性而继续坚持”？
   - 应该重构架构，还是继续修补症状？

   **继续尝试前，与人类协作者讨论。**

   这不是假设失败，而是架构错误。

## 危险信号——停止并遵循流程

如果发现自己在想：

- “先快速修一下，以后再调查”
- “改改 X 看是否有效”
- “一次加多个变更，再跑测试”
- “跳过测试，手工验证就行”
- “大概是 X，我来修”
- “还没完全理解，但这样也许有效”
- “模式要求 X，但我换种方式适配”
- “主要问题如下：[没有调查就列出修复]”
- 尚未追踪数据流就提出方案
- **“再试一次修复”**（已经尝试 2 次以上）
- **每次修复都在不同位置发现新问题**

**以上任何一种都意味着：停止，回到第一阶段。**

**3 次以上修复失败：**质疑架构（见第四阶段第 5 项）。

## 人类协作者提示你做错了

**留意这些纠正：**

- “那不是已经发生了吗？”——你未经核验就作了假设
- “这能告诉我们……吗？”——你本应增加证据收集
- “别猜了”——你在尚未理解时提出修复
- “深入想想”——质疑基础，而不只是症状
- “我们卡住了吗？”（沮丧）——当前方法没有奏效

**看到这些信号时：**停止，回到第一阶段。

## 常见借口

| 借口 | 事实 |
|---------|---------|
| “问题很简单，不需要流程” | 简单问题也有根因。对于简单 bug，该流程很快。 |
| “紧急情况，没时间走流程” | 系统化调试比猜测和试错更快。 |
| “先试这个，再调查” | 第一次修复会决定后续模式。从一开始就做对。 |
| “先确认修复有效，再写测试” | 未测试的修复无法持久。测试优先才能证明它。 |
| “一次改多个地方能省时间” | 无法确定哪个变更有效，还会制造新 bug。 |
| “参考太长，我直接适配模式” | 只理解一部分必然产生 bug。完整阅读。 |
| “我看到问题了，先修” | 看到症状不等于理解根因。 |
| “再试一次修复”（已失败 2 次以上） | 3 次以上失败说明架构有问题。质疑模式，不要继续修补。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解发生了什么以及为什么 |
| **2. 模式** | 寻找可用示例并对比 | 识别差异 |
| **3. 假设** | 形成理论并最小化测试 | 假设得到确认，或产生新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 已解决，测试通过 |

## 流程得出“没有根因”时

如果系统化调查显示问题确实来自环境、时序或外部系统：

1. 你已经完成该流程
2. 记录调查过的内容
3. 实现适当处理（重试、超时、错误消息）
4. 添加监控或日志，为未来调查保留证据

**但是：**95% 的“没有根因”其实是调查不完整。
