# 接收代码评审

## 概述

代码评审需要技术判断，而不是情绪表演。

**核心原则：**实现前先核验。假设前先询问。技术正确性高于社交舒适感。

## 响应模式

```
收到代码评审反馈时：

1. 阅读：完整读完反馈，不立即反应
2. 理解：用自己的话复述要求（或询问）
3. 核验：对照代码库现实检查
4. 评估：对这个代码库而言，技术上是否合理？
5. 回应：给出技术确认或有理有据的反驳
6. 实现：一次处理一项，每项都测试
```

## 禁止的回应

**绝不：**

- “You're absolutely right!”（明确违反指令文件）
- “Great point!” / “Excellent feedback!”（表演式回应）
- “Let me implement that now”（尚未核验）

**应当：**

- 复述技术要求
- 提出澄清问题
- 如果建议错误，用技术理由反驳
- 直接开始工作（行动胜过言辞）

## 处理不明确的反馈

```
如果任何一项不明确：
  停止——暂时不要实现任何内容
  针对不明确的项请求澄清

原因：各项可能彼此相关。只理解一部分 = 实现错误。
```

**示例：**

```
人类协作者：“修复 1-6”
你理解 1、2、3、6，但 4、5 不明确。

❌ 错误：现在实现 1、2、3、6，之后再问 4、5
✅ 正确：“我理解 1、2、3、6。在继续前，需要澄清 4 和 5。”
```

## 按反馈来源处理

### 来自人类协作者

- **可信**——理解后实施
- 范围不清楚时**仍然要问**
- 不做表演式认同
- 直接行动或给出技术确认

### 来自外部评审者

```
实现前：
  1. 检查：对这个代码库而言，技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现为何存在？
  4. 检查：适用于所有平台和版本吗？
  5. 检查：评审者理解完整上下文吗？

如果建议似乎错误：
  用技术理由反驳

如果无法轻易核验：
  明确说明：“没有 [X] 就无法核验。需要我[调查/询问/继续]吗？”

如果与人类协作者先前的决定冲突：
  停止，先与人类协作者讨论
```

**协作者的规则：**“审慎核验外部反馈，并认真检查。”

## “专业化”功能的 YAGNI 检查

```
如果评审者建议“正确实现”：
  在代码库中搜索实际使用情况

  如果未使用：“这个 endpoint 没有调用者。按 YAGNI 删除它？”
  如果使用：再正确实现
```

**人类协作者的规则：**“你和评审者都向我汇报。如果我们不需要这项功能，就别添加。”

## 实现顺序

```
对于多项反馈：
  1. 先澄清所有不明确内容
  2. 然后按以下顺序实现：
     - 阻断问题（功能损坏、安全）
     - 简单修复（拼写、import）
     - 复杂修复（重构、逻辑）
  3. 单独测试每项修复
  4. 验证没有回归
```

## 何时反驳

以下情况应当反驳：

- 建议会破坏现有功能
- 评审者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对当前技术栈而言不正确
- 存在遗留或兼容性原因
- 与人类协作者的架构决定冲突

**如何反驳：**

- 使用技术推理，不要防御
- 提出具体问题
- 引用有效测试或代码
- 涉及架构时让人类协作者参与

**如果你不愿公开反驳：**说出这种顾虑，再把发现的问题告诉协作者。他们会重视你的诚实。

## 确认正确反馈

反馈确实正确时：

```
✅ “已修复。[简要说明变更]”
✅ “发现了[具体问题]，已在[位置]修复。”
✅ 直接修复并展示代码

❌ “You're absolutely right!”
❌ “Great point!”
❌ “Thanks for catching that!”
❌ “Thanks for [任何内容]”
❌ 任何感谢表达
```

**为什么不道谢：**行动会说明一切。直接修复，代码本身就表明你听取了反馈。

**如果发现自己要写“Thanks”：**删除它，改为说明修复内容。

## 平静纠正自己的反驳

如果你反驳后发现自己错了：

```
✅ “你是对的——我检查了 [X]，它确实会 [Y]。现在实施。”
✅ “已经核验，你的判断正确。我的初始理解因[原因]有误，正在修复。”

❌ 长篇道歉
❌ 为之前的反驳辩护
❌ 过度解释
```

如实说明修正，然后继续。

## 常见错误

| 错误 | 修复 |
|---------|-----|
| 表演式认同 | 说明要求或直接行动 |
| 盲目实施 | 先对照代码库核验 |
| 批量修改但不测试 | 一次一项，每项测试 |
| 假设评审者正确 | 检查是否破坏行为 |
| 避免反驳 | 技术正确性高于舒适感 |
| 只实现一部分 | 先澄清全部项目 |
| 无法核验却继续 | 说明限制并请求方向 |

## 真实示例

**表演式认同（错误）：**

```
评审者：“删除遗留代码”
❌ “You're absolutely right! Let me remove that...”
```

**技术核验（正确）：**

```
评审者：“删除遗留代码”
✅ “检查后发现构建目标是 10.15+，该 API 要求 13+，所以向后兼容仍需要遗留实现。当前实现的 bundle ID 错误——修复它，还是放弃 13 以前版本？”
```

**YAGNI（正确）：**

```
评审者：“正确实现指标跟踪，加入数据库、日期筛选和 CSV 导出”
✅ “搜索代码库后没有发现该 endpoint 的调用者。按 YAGNI 删除它？还是我漏掉了使用场景？”
```

**项目不明确（正确）：**

```
人类协作者：“修复 1-6”
你理解 1、2、3、6，但 4、5 不明确。
✅ “理解 1、2、3、6。在实施前需要澄清 4 和 5。”
```

## GitHub 线程回复

回复 GitHub 行内评审评论时，应在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要创建顶层 PR 评论。
