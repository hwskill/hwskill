# 完成前验证

## 概述

**核心原则：**永远先有证据，再作声明。

**违反规则的字面要求，也就是违反规则的精神。**

## 铁律

```
没有新鲜的验证证据，就不能声称完成
```

如果你没有在当前消息中运行验证命令，就不能声称它通过。

## 门函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能证明这项声明？
2. 运行：执行完整命令（新鲜、完整）
3. 阅读：阅读完整输出，检查退出码和失败数量
4. 核验：输出是否证实该声明？
   - 如果否：根据证据说明实际状态
   - 如果是：在声明中附上证据
5. 只有到这时：才能作出声明

跳过任何一步，所得结论就不构成验证。
```

## 常见失败

| 声明 | 需要 | 以下证据不充分 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 个失败 | 上一次运行、“应该会通过” |
| Linter 无问题 | Linter 输出：0 个错误 | 局部检查、推断 |
| 构建成功 | 构建命令退出码为 0 | Linter 通过、日志看起来正常 |
| Bug 已修复 | 原始症状测试通过 | 修改了代码、假定已经修复 |
| 回归测试有效 | 已验证 RED→GREEN 循环 | 测试只通过一次 |
| Agent 已完成 | VCS diff 显示变更 | Agent 报告“成功” |
| 满足要求 | 逐行检查清单 | 测试通过 |

## 危险信号——停止

- 使用“应该”“大概”“似乎”
- 验证前就表达满意（“很好！”“完美！”“完成了！”等）
- 即将提交、推送或创建 PR，但尚未验证
- 相信 Agent 的成功报告
- 依赖局部验证
- 认为“这次例外”
- 因疲惫而想尽快结束
- **任何暗示已经成功却没有运行验证的措辞**

## 防止找借口

| 借口 | 事实 |
|---------|---------|
| “现在应该可以了” | 运行验证。 |
| “我很有信心” | 信心不等于证据。 |
| “就这一次” | 没有例外。 |
| “Linter 通过了” | Linter 不等于编译器。 |
| “Agent 说成功了” | 独立验证。 |
| “我累了” | 疲惫不是理由。 |
| “局部检查就够了” | 局部检查什么也证明不了。 |
| “换个说法，规则就不适用” | 精神高于字面。 |

## 关键模式

**测试：**

```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “现在应该能通过” / “看起来正确”
```

**回归测试（TDD RED→GREEN）：**

```
✅ 编写 → 运行（通过）→ 撤销修复 → 运行（必须失败）→ 恢复修复 → 运行（通过）
❌ “我已经写了回归测试”（但没有验证 RED→GREEN）
```

**构建：**

```
✅ [运行构建] [看到：退出码 0] “构建通过”
❌ “Linter 通过了”（Linter 不检查编译）
```

**要求：**

```
✅ 重读计划 → 创建检查清单 → 逐项验证 → 报告缺口或完成情况
❌ “测试通过，所以阶段完成”
```

**Agent 委派：**

```
✅ Agent 报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 相信 Agent 报告
```

## 何时应用

在以下情况之前**始终**应用：

- 任何形式的成功或完成声明
- 任何满意表达
- 任何有关工作状态的正面陈述
- 提交、创建 PR、完成任务
- 进入下一项任务
- 向 Agent 委派

**规则适用于：**

- 完全相同的措辞
- 改写和同义表达
- 言外之意
- 任何暗示完成或正确的沟通
