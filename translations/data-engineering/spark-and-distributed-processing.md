# Spark 与分布式处理

## 概述

对于超出单机处理能力、需要严谨分布式执行的批处理工作负载，请使用本技能。它帮助 Agent 分析 `Spark`、`Glue` 和 `EMR` 等托管 Spark 服务、分区、连接、存储布局以及故障安全处理。

## 使用时机

- 构建或修改 `Spark` 作业
- 在 `Spark`、`Glue`、`EMR` 或更小型的引擎之间进行选择
- 调试代价高昂的连接、数据倾斜、shuffle 或内存问题
- 为大型文件或分区表设计批处理流水线
- 对 `Iceberg`、`Delta` 或 `Hudi` 等湖仓表实现转换

对于能够轻松放入单个进程的轻量本地转换，不要使用本技能。

## 工作流

1. 确认确实需要分布式执行。检查：

   - 输入数据量
   - 延迟预期
   - 转换复杂度
   - 文件大小和分区数量
   - 与更简单引擎相比的成本

2. 有意识地选择运行时。

   - `Spark`：提供直接控制和广泛的生态系统支持
   - `Glue`：AWS 原生托管 Spark 执行
   - `EMR`：为 Spark 及相关引擎提供更广泛的集群控制
   - 短时或无服务器 Spark（`Lambda`、无服务器 `Glue`、严格的超时上限）：加载 `spark-serverless-reliability-and-state-management`

3. 设计物理计划，而不仅是逻辑计划。需要考虑：

   - 分区和文件布局
   - shuffle 密集型连接
   - 倾斜键
   - 检查点或中间持久化
   - 写入模式和幂等行为

4. 在边界处明确数据契约。在执行代价高昂的计算前验证输入假设，并在发布前验证输出契约。

5. 保证回填和重新运行安全。历史批次重算应明确规定覆盖、合并或追加语义。

## 常见借口

| 借口 | 事实 |
|---|---|
| “Spark 会替我们处理优化。” | 引擎优化会有所帮助，但糟糕的分区、数据倾斜和写入策略仍会导致失败或产生巨额成本。 |
| “直接扩容集群就行。” | 扩容往往只是掩盖糟糕的物理设计，而且仍可能因倾斜或低效 shuffle 失败。 |
| “使用托管 Spark 就不需要设计运行时。” | `Glue` 和 `EMR` 仍然需要有意识地设计分区、重试和存储策略。 |

## 危险信号

- 选择 `Spark` 时没有规模或延迟方面的理由
- 未定义分区和写入策略
- 连接没有考虑倾斜的业务键
- 历史加载的重新运行行为不明确
- 在更小型引擎更简单且更便宜的场景中使用分布式计算
