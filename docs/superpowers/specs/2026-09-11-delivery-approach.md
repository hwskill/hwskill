# 技能共享平台整体推进与交付方案

日期：2026-09-11

状态：按最新三条备注再次收敛，待重新确认。本文件是整体推进提案，不是已开始执行的实施计划。用户确认前不启动实现、子 Agent、仓库切换或远端发布。

## 1. 完整交付目标

落实已确认的需求规格与技术设计，交付可构建、可测试、可按文档部署和使用的技能共享平台，包含：

- hosted/external 技能目录、独立推荐帖、Schema、模板与 Agent 贡献流程。
- 中文网站、目的搜索与筛选、推荐展示、一句话安装与首次使用说明、可选 Star badge。
- 分层验证、静态产物构建、发布日志和失败恢复。
- Python 信息获取、校验、筛选、增量判断、去重和结构化输出，包含读取失败恢复与增量状态持久化；提交给 bot 的 SDK/HTTP 方式后续确定，本期不实现发送层。
- 首批经过来源调研、适用性筛选和分层验证的技能起始数据，不仅提供演示条目。
- 同仓库换代、旧版固定标签与可用安装说明、新版清理旧运行时。
- 中文部署指导、开发指引、使用说明、贡献指南、维护手册、迁移说明及验收报告。
- 关键设计、复杂逻辑和反直觉行为的中文代码注释。

以需求 REQ-01 至 REQ-10 逐项记录交付证据。最小闭环是开发检查点，不是缩减最终范围。按最新范围调整，信息提供模块的完成标准是 Python 获取、检查、筛选、增量与输出的完整验证，以及后续调用文档。bot 提交、发送适配、群卡、签名和群联调不属于本期实现，不以它们作为完成门槛。

## 2. 模型与协作方式

### 推荐分工

| 工作类型 | 推荐模型/推理档位 | 使用边界 |
| --- | --- | --- |
| 长期统筹、任务追踪、集成、阶段报告与验收组织 | gpt-5.6-sol / medium | 主统筹；以持久任务记录维持进度，常规推进不依赖 Astra |
| 常规 Python/TypeScript 实现与模块测试 | gpt-5.6-terra / medium | 默认实现模型；需求清楚、文件范围明确 |
| 发布恢复、增量交接幂等、迁移和关键审阅 | gpt-5.6-sol / high | 优先用于推理与返工成本高的环节 |
| 术语统一、文档整理、示例批量补齐 | gpt-5.6-luna / low | 只做已有依据、可自动核对的任务；不独立决定架构或编造操作命令 |
| 员工视角的安装、校验、代贡献验收 | gpt-5.6-luna / medium，干净配置 | 独立测试进程，只读取公开指引，不继承开发上下文 |
| 架构裁决、复杂故障、跨模块争议 | gpt-6-astra / high 专项专家 | 有具体问题和证据包时调用，返回结论后结束专家任务 |

当前可用工具列出了上述模型。官方将 Terra 定位为智能与成本平衡、Luna 定位为成本敏感任务，Sol 适合复杂专业工作；实际任务成本取决于上下文、推理和返工，不能把 API 单价直接换算成本次 Codex 账户消耗。[官方模型目录](https://developers.openai.com/api/docs/models)、[Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra)、[Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)

Sol / medium 作为统筹是本项目推荐起点，不是声称已有该项目长线运行实测。主任务的模型设置由应用控制；执行前需将主任务设为 Sol / medium，本轮不声称已完成切换。Astra 采用按需专家调用，不作为持续轮询和转发任务的外层协调器。

统筹将模块状态、当前 commit、通过/失败的检查、下一步、阻碍和设计决定写入项目进度文档；在阶段结束、发生阻碍及上下文交接前更新。恢复时读取该状态及相关差异，而非重读全部历史或让各模型自行推断进度。关键接口以已确认规格为准，Astra 裁决后由 Sol 记录并下发。

### 成本控制

- 默认最多两个实现子 Agent 并行，加一个主 Agent 协调。只并行文件和状态不冲突的任务，保留审阅余量。
- 先冻结 Schema 和跨模块输入输出，再并行网站与工具实现；共享 Schema、依赖锁和集成变更统一由指定负责人修改。
- 每个子任务给出明确目标、文件所有权、必要文档段落、测试命令和完成条件；采用独立短上下文，不默认复制全部对话。
- 小修改合并为可独立验收的模块任务；规格符合性和代码质量都检查，但不为每个文案改动开多轮审阅。
- 一次定向修复后若同一技术障碍仍未解决，重新诊断并按需要升级模型/调整方案，不盲目重复同一尝试。
- 定向测试通过后按阶段跑集成回归；没有新变化不重复跑昂贵 Agent 验证。
- 文档和数据格式先用确定性工具检查，模型专注语义、设计和未知行为。
- 记录可取得的阶段用量、运行时间与返工原因；无法取得精确归因时如实说明，不虚构节省百分比。没有用户预算时不设任意完成上限，也不以省成本为由省略验收。

## 3. 阶段与检查点

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 0：基线与实施准备 | 固定旧版基线、本地标签、新版分支、规格存档、模块计划与设施参数清单 | 旧工作可追溯，当前未提交文档保留，任务边界和操作范围明确 |
| 1：目录与贡献 | 技能/推荐 Schema、模板、校验器、规范化产物、中文贡献指引；首批技能调研与候选目录 | 双来源与三类贡献验证；来源与适用性有依据；草稿、重复、错误引用有明确结果 |
| 2：发现与安装 | Astro 网站、Pagefind、推荐页、静态安装说明、badge 降级、筛选后的起始数据 | 中文/英文混合检索可用；干净 Luna 完成双来源安装与代贡献；形成可演示闭环 |
| 3：验证与发布 | 验证记录、不可变发布目录、事件日志、撤回和恢复逻辑 | 版本错配不误报通过，构建失败不通知，重试/回滚不重复新增事件 |
| 4：信息提供与部署 | Python 获取/校验/筛选/增量输出、状态恢复、部署资产与调用说明 | 静态读取、数据检查、过滤与撤回、可重复输出、读取失败与重启恢复；无 bot 发送依赖 |
| 5：迁移与完整交付 | 新版清理旧内容、固定旧版入口、中文文档全集、验收报告和可审阅迁移变更 | REQ-01..10 均有证据，文档命令在对应环境实际验证，无未解释缺口 |

实施顺序以依赖为准：阶段 1 的契约稳定后，网站和通知协议可分工开发；发布日志契约未稳定时不让多个模块各自推断接口。每阶段由主 Agent 检查、集成和报告，通过后自动进入下一阶段，不把每个小任务都变成用户确认点。

需要用户重新决定的事项限于目标/架构明显变化、真实设施缺失、不可兼容的部署约束，或原授权范围外的外部操作。技术细节按已确认方案自主处理。

### 首批技能起始数据

初版正式收录 5–10 个高质量技能，围绕开发者领域选择：通用计算、智能计算、性能优化、大数据、C++/Python，以及常用周边任务（例如制作 PPT）。不要求每个主题或 L1–L5 每层都凑一个。调研可覆盖更多候选，保存来源、调研日期、采纳/暂缓理由和适配情况，供后续扩充参考；不以完成固定候选数量拖慢开发，也不把单一上游的子技能当作全部覆盖。

调研优先阅读官方/作者来源、实际说明与安装机制，记录调研日期、来源、维护活跃度、可核实的社区采用或评价、适用 Agent/模型和限制。仓库 Star 只是辅助信号，不能替代使用人数或实际兼容验证。明确与当前 Agent 原生能力的重叠、强制流程冲突、脚本/工具依赖，不推荐默认一次安装全部候选。

元数据与来源检查覆盖所有正式收录项；按安装机制和声明环境选择实际 Luna 验证，首页精选优先使用有安装/使用证据的条目。未验证项保留真实状态，涉及特别硬件、账号或模型能力的技能不虚标通用。外部条目不备份正文，候选调研记录与网站面向员工的简介分开保存。

## 4. 仓库与变更管理

确认方案后，先保存新规格并在旧实现 commit 上建立固定旧版标签，再建立 codex/ 前缀的新版开发分支。默认复用当前工作目录，不为每个子任务创建新仓库或用户侧新任务；若并行写入确实需要隔离，在同仓建立必要的本地 worktree，并记录归属。

分阶段形成聚焦的本地提交，源码、测试和对应文档一起提交；不混入无关文件或凭据。主线在迁移准备完成前不切换。需要重构的公共代码仅随真实新用途迁移，旧运行时最终退出新版工作树，不建立长期 legacy 层。

远端推送、PR 创建、主线合入、正式部署和群消息发送在已有明确授权及实际环境范围内执行；尚无授权的外部操作，先准备可审阅结果再集中确认。最终迁移提交必须列出删除范围和旧版回退方式，不在用户尚未确认整体推进时提前执行。

## 5. 文档与代码注释标准

文档以中文呈现，文件名、代码标识符、标准协议名和命令保持原名。建议交付位置：

| 文档 | 内容 |
| --- | --- |
| README.md | 项目定位、面向不同角色的入口、快速开始 |
| CONTRIBUTING.md | 收录/推荐/修正模板，Agent 一句话贡献，PR 与权限流程 |
| docs/guides/user-guide.md | 搜索、安装、首次使用、发布推荐、失败处理 |
| docs/guides/deployment-guide.md | 静态站、CI 构建发布、区域任务、持久卷、凭据、上线与回滚 |
| docs/guides/development-guide.md | 目录结构、模块职责、Schema/接口、开发环境、测试、新来源/群适配扩展 |
| docs/guides/operations-guide.md | 发布失败、来源失效、推荐撤回、来源读取限流、状态备份恢复及故障排查 |
| docs/guides/migration-guide.md | 旧版固定入口、版本差异、旧内容处理、新旧切换与回退 |
| docs/validation/acceptance-report.md | 版本、环境、需求覆盖、实际执行记录与未验证项 |

文档随模块实现更新，最后再执行通读和命令复现，不等代码全部完成后临时编写。由轻量模型整理的操作步骤必须以实际脚本和执行结果校核。

关键代码用中文说明“为什么这样设计、必须守住什么条件、改错会导致什么后果”。重点包括：

- 发布候选时间与 committed_at 的区别、日志和网站切换顺序。
- cursor 表示已确认交接的区间；批次可重复获取与确认的幂等约束。
- 普通推荐编辑不重复推广、撤回与待交接信息重算。
- 来源/安装声明变化使哪些验证结果失效，文案修改为何不重跑安装。
- 公开静态读取无需 Token，私有仓库读取与贡献写入凭据为何分开。
- 为什么旧安装脚本 URL 固定到标签仍可能继续获取 main。

简单语句不逐行复述；公共接口说明输入输出和异常，复杂不变量就近注释，并配能证明行为的测试。禁止用“临时处理”“应该没问题”等模糊注释掩盖未解决问题。

## 6. 验证与完成口径

每个模块完成后检查需求符合性、关键代码质量、中文文档与注释。关键状态机测试覆盖正常流程、失败、重试、撤回、回滚和并发冲突；网站验证覆盖搜索、筛选、复制、基础可访问性和异常降级。

部署资产至少在干净环境按文档构建和启动，验证无隐藏本机依赖。Agent 验收固定使用干净配置的 Luna / medium：新会话、临时 HOME/项目目录、不挂载开发者技能库、不继承本次对话和旧 Profile/Hook/MCP；只提供员工能获得的一句话任务、站点/贡献指引及必要最小认证。宿主版本、模型与配置记录在报告中。

Luna 执行真实安装、调用校验器、准备收录/推荐/修正变更；确定性检查和独立观察器确认文件位置、完整资源、宿主识别、Schema 结果、变更范围与期望业务输出，不以 Luna 自述成功代替证据。贡献提交使用本地测试远端或获准沙箱，本期不由测试自动向真实公共仓库发 PR。

优化对象包括简短且意图明确的入口提示词、机器可读索引、按任务拆分的贡献/安装指引、有效模板、一次返回完整问题清单的校验器和可重复执行的辅助脚本。优先让确定性工具承担解析与检查，减少 Agent 无目的遍历、重复询问和反复修正。所有辅助资源必须是普通员工可获得的正式仓库/网站资源，而非测试专属提示。

使用固定任务与干净环境比较优化前后成功率、工具调用次数、人工介入、耗时及可取得的 token 用量，同时保留未用于调优的样例做回归。只有优化涉及相关路径或出现失败时才重跑昂贵验证；不为单项指标反复大规模试验，也不通过省掉必要检查来降低表面成本。

Luna 失败先区分产品指引问题、环境问题和模型能力限制。优化通用指引后重跑；若用 Sol/Astra 诊断或对照，单独标注，不能将高阶模型成功替换 Luna 的验收结果。受测技能自身要求更强模型时如实声明，不强求所有技能行为都在 Luna 上通过。

完整交付需满足：本期约定功能已实现、对应测试通过、关键问题关闭、中文文档与代码一致、首批技能已整理、旧版可追溯、迁移变更可审阅。信息模块按最新范围验收获取、检查、筛选、增量和输出，可完成本期交付；提交给 bot 的方案和正式群联调后续决定，不作为本期未知依赖反复阻塞。

### Python 信息提供与容错

本期只实现获取发布信息、校验格式/版本/完整性、按用途与生命周期筛选、比较增量、去重和合并相关信息，并以 Python 返回值及 JSON 文件提供下游所需的数据。输出含稳定 ID、变更类型、标题、摘要、技能引用、来源版本、详情/安装说明链接与状态，不生成特定平台 payload。

保留一个小而明确的交接边界：生成待处理批次后，调用方确认已接收才推进对应增量游标；确认表示信息交接完成，不表示群消息已发送。失败可重新取得待处理结果，默认不静默吞掉尚未交接的数据。具体函数与数据契约在实施计划中固定，不先建设通用 bot 框架。

容错覆盖获取超时、暂时错误/限流、无效数据、未知版本、增量缺口、重复事件、写入中断和进程重启。测试使用静态 feed fixture 或本地 feed 服务，不建设 bot 模拟服务。后续代码可消费相同输出，自行选择 SDK 调用或 HTTP 请求；平台认证、签名、业务成功判定、群限流和发送重试届时实现。

## 7. 实施期间需要落实的输入

在阶段 0 整理，并在对应联调前落实：蓝区 Git/CI 平台与部署位置、静态站域名/基路径、区域任务运行环境与持久卷、可用 Luna 测试宿主与最小认证、声明支持的 Agent/系统组合。实际群平台及接口属于后续接入输入，本期无需提供真实 Webhook 或群 Token。

这些输入不要求用户一次全部提供。先完成不依赖设施的模块；信息提供模块依 fixture/本地 feed 完成约定验收，后续 bot 提交只依赖稳定数据输出，不通过猜测宣称平台兼容或已上线。

请求重新确认：Sol / medium 长期统筹、Astra 按需专家、Terra 常规实现、干净 Luna 员工体验验收、首批 5–10 个开发者技能及保留调研记录、提示词/仓库资源优化、Python 信息提供为止的完成边界；以及既定有限并行、中文交付与注释、本地标签/分支/阶段提交策略。确认并将主任务模型设为 Sol / medium 后，制定模块实施计划并开始执行；本轮不开始实现。
