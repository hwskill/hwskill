# 技能共享平台技术选型与方案设计

日期：2026-09-11

状态：架构与契约细化稿，待技术评审；未实施。产品方向、PR 提交流程、独立推荐帖与 badge 优先策略已确认；框架选型和下文接口为推荐设计。产品依据为同目录的 `2026-09-11-cross-project-skill-sharing-design.md`。

## 1. 推荐结论与约束

采用 Git 管理内容、Astro 生成静态网站、Pagefind 提供浏览器搜索、Python 完成确定性校验与发布产物构建。员工已有 Agent 负责辅助贡献，各安全区运行独立 Python 信息任务，使用本区 SQLite 保存增量与交接状态；bot 发送层本期不实现。

蓝区网站不需要业务数据库或常驻应用后端。静态页面、技能元数据、贡献指引和 feed 按可直接读取设计，无需 AccessToken，不自建站点账号或认证网关。访问非公开 Git 仓库及提交 PR 时才使用实际 Git 平台认证。各区的反馈入口指向本区已有设施，不由蓝区页面直接向高区服务发请求。

实施假设：蓝区可运行 Python 与 Node 构建任务并托管静态文件；高区有可持久化状态的任务运行环境；浏览器、Agent 和机器人能够直接读取静态说明与 feed，非公开技能源另按仓库权限认证。以上网络和部署条件尚未通过实际设施验证。具体 Git/CI、群平台和部署设施未确定，不把任一云服务或群接口写成既定事实。

规模先用 1,000 个技能和 10,000 个技能的构造数据评估，不把此数量当作已知业务规模或已验证容量。

## 2. 选型比较

| 方案 | 收益 | 成本与边界 | 结论 |
| --- | --- | --- | --- |
| Astro 静态目录＋Python 工具 | 卡片、筛选、详情和机器可读文件可统一生成；服务端运行简单 | 需要维护 Node 和 Python 两套构建依赖 | 推荐 |
| VitePress 文档站＋Python 工具 | 文档导航、贡献说明容易起步 | 本项目重点是技能发现与卡片交互，定制目录仍需要开发 | 如果产品缩减为文档导航站可选 |
| 带数据库的业务网站 | 可直接承接登录、点赞、个性化和在线投稿 | 新增认证、接口、数据库、备份和跨区写入治理 | 有明确实时互动需求后再增加 |

Astro 能在构建期从结构化文件生成静态页面，适合本项目读多写少的目录；这是结合需求的选型判断，不是已完成的性能验证。[官方内容集合文档](https://docs.astro.build/en/guides/content-collections/)

VitePress 是支持自定义 Vue 组件的静态站点生成器；这里选择 Astro 是为了围绕目录页面组织开发，而非认为 VitePress 无法实现。[官方介绍](https://vitepress.dev/guide/what-is-vitepress)

### 具体技术与版本策略

| 部分 | 选择 | 理由与约束 |
| --- | --- | --- |
| 人工元数据 | YAML＋JSON Schema Draft 2020-12 | 人和 Agent 共用模板，单一规范 |
| 校验/目录构建 | Python、PyYAML、jsonschema | 沿用现有 Python 代码与测试习惯 |
| 网站 | Astro、TypeScript、普通 CSS | 静态输出；交互只用于搜索、筛选和复制，不默认增加完整 UI 框架 |
| 搜索 | Pagefind extended 构建＋前端 API | 随站点发布静态索引，支持中文分词与筛选 |
| 贡献辅助 | CONTRIBUTING.md、模板、Schema、本地校验入口 | 员工 Agent 准备 PR；首版不依赖中心化模型服务 |
| CI/CD | 可移植脚本＋现有 CI 的薄适配层 | 不把业务逻辑绑定某 CI 配置语法 |
| 蓝区部署 | 已有静态托管；容器环境可使用静态 HTTP 服务 | 静态读取无需 Token；HTTPS 与网络入口复用现有设施 |
| 信息提供 | Python 单次运行任务/库接口＋SQLite | 获取、检查、筛选、增量与输出；bot 提交方式待定 |
| 验证 | 本地离线检查＋受控隔离任务 | 复用现有测试设施中适用部分，不把当前运行链路作为安装要求 |

不盲目锁定“最新版”。Python 保留仓库现有 >=3.10 兼容目标，构建镜像固定一个实际支持版本；Node 基线需满足所选 Astro 版本。当前官方安装文档给出的最低版本为 Node 22.12.0；实施时选组织可用且仍受支持的偶数版本，并锁定 Astro、Pagefind、Python 依赖和构建镜像。[Astro 安装要求](https://docs.astro.build/en/install-and-setup/)

核心站点资源、搜索文件和字体均同源提供，不依赖浏览器访问外部 CDN。动态 Star badge 是可选外部展示，按部署区域允许的来源启用，失败不影响核心流程。内网构建从已配置的依赖镜像取得锁定依赖，不能假定 CI 能访问公网。

## 3. 组件与数据流

```text
员工 Agent / 轻量推荐入口
          ↓ 条目草稿与证据
Git PR → 离线校验 → 审阅合入
                         ↓ 固定 commit
                 Python 目录构建器
                         ↓ catalog + 安装说明 + 贡献材料
                  Astro → Pagefind
                         ↓ 不可变发布目录
                蓝区静态网站 → 就绪检查 → 发布日志
                                                ↑ 静态 feed 直接拉取
                                      黄区/绿区 Python 信息任务
                                                ↓ 增量/交接状态
                                          结构化输出
                                                ↓ 后续决定提交方式
                                             本区 bot

受控验证任务 → 带版本的验证报告 → 下一次发布输入
```

### 文件边界（拟新增）

| 路径 | 职责 |
| --- | --- |
| `entries/<layer>/<namespace>/<name>.yaml` | 唯一人工技能条目 |
| `skills-src/` | hosted 技能正文；迁移期间旧快照另行处理 |
| `schemas/entry.schema.json` | 条目契约 |
| `schemas/catalog.schema.json`、`verification.schema.json`、`release.schema.json` | 跨组件产物契约 |
| `templates/entries/`、`templates/recommendations/`、`CONTRIBUTING.md` | Agent 可直接读取的贡献材料 |
| `curation/` | 主题定义、精选选择和相关词；推荐正文只存 Recommendation，非运行时 Profile |
| `recommendations/<id>.yaml` | 首次或后续推荐帖，一篇可关联多个技能 |
| `schemas/recommendation.schema.json` | 推荐帖契约；投稿与 Agent 共用 |
| `src/hwskill/directory/` | 新条目读取、校验、去重与生成；不依赖 MCP 初始化 |
| `src/hwskill/sharing/` | feed 读取、检查、筛选、增量和结构化输出 |
| `site/` | Astro 页面、样式与搜索交互；只读取规范化产物 |
| `scripts/directory/` | 校验、构建、发布和迁移的可移植入口 |
| `tests/directory/`、`tests/sharing/` | 新模型与信息交接契约测试 |

生成目录忽略于 Git；有意发布的产物进入独立发布存储。旧 `registry/catalog.json` 不直接改写为网站格式，防止破坏现有运行时消费者。

## 4. 元数据与校验契约

条目沿用需求文档字段，新增技术约束：

- `schema_version` 固定明确格式版本；`id` 为稳定 namespace/name，与 layer 独立。
- `source.kind` 为 hosted 或 external。hosted 必须给出仓库安全相对路径；external 指定来源类型、URL、技能定位及安装机制。
- Git 来源拆分 `repository`、`path`、`requested_ref`，验证报告记录 `resolved_revision`；非 Git 来源不能伪造 commit，记录其实际版本和可取得的内容摘要。
- 兼容声明与验证结果分离：声明支持某 Agent 不等于在该 Agent 上验证通过。
- 可未知的字段显式表示未知；缺少来源或技能定位的推荐先留在接收队列。安装方式不明确的已收录条目不能生成可执行的安装动作。
- `install` 包含安装方式、影响范围和上游指引，不接受任意 shell 字符串作为可信自动执行任务。
- 描述只允许文本或有限 Markdown，禁止贡献条目携带 MDX/脚本执行能力。

YAML 解析采用安全加载并拒绝重复键，限定为 JSON 可表示的数据类型；Schema 验证之外，显式检查 ID 唯一性、路径越界、URL scheme、来源重复、hosted 引用完整性和字段间关系。路径和来源规范化不能随意删除大小写或查询参数导致不同来源合并；相同规范化仓库地址＋技能路径为强重复候选，同名只提示。

唯一结构规范为 JSON Schema；Python 实施验证，网站消费已验证 JSON，不再手写第二套同语义 Zod 规则。前端类型可从规范生成或由固定映射测试约束。jsonschema 支持按草案选择校验器，但 `format` 默认不执行验证，因此 URL 和日期等必须配置实际检查并有负例测试。[jsonschema 验证文档](https://python-jsonschema.readthedocs.io/en/stable/validate/)

本地和 CI 共用检查，输出机器可读问题列表：`file`、`field`、`code`、`severity`、`message`、`suggested_action`。离线检查不拉上游、不调用模型、不运行条目声明的脚本；联网检查另行触发。这样 Agent 能一次修正常规问题，维护者只看差异和异常。

## 5. 贡献方案

网站提供“复制贡献指引”，员工将来源交给已有 Agent。Agent 读取 Schema、模板、现有 catalog 和示例，生成条目并调用确定性校验；可使用其已有获准的 Git 平台工具准备 PR，不为所有员工强制安装新的 CLI 或技能。

首版降低平台成本的方式是提供可靠规范和自动检查，而非维护一个能理解所有技能网站的中心化爬虫。支持的常见来源可增加确定性元数据提取器，其他来源由 Agent 根据材料整理；模型生成的分类和摘要是建议，不是验证证据。

只提交链接的员工通过现有本区群/表单进入队列；维护者可一次把一批线索交给 Agent 生成多个条目和汇总检查报告。每条线索以已有接收设施的记录 ID 跟踪状态，重复项直接关联现有技能；无需首版开发独立投稿数据库。具体接收入口部署时配置，不在无写权限的静态页面上假装已提交。

高区内容不自动回写蓝区。蓝区写入权限、用户对提交的授权和待发布内容的流转条件独立检查，不能复用通知只读 Token 作写入凭据。

## 6. 网站、搜索与安装入口

页面：`/` 为新技能和精选；`/skills/` 为目的检索与筛选；`/skills/<namespace>/<name>/` 为稳定详情；`/topics/<slug>/` 为主题精选；`/contribute/` 为贡献入口。

机器可读文件：`/data/catalog.json`、`/schemas/entry.schema.json`、`/contribute/agent.md` 以及每个发布版本中的技能安装 JSON/Markdown。浏览器和 Agent 直接读取这些静态文件，无需 AccessToken，也不依赖执行网页 JavaScript。仓库非公开时，获取仓库内容才需要相应读取权限；不能把仓库认证要求扩展为静态站点的前置条件，或将仓库 Token 嵌入前端或复制文本。

读取边界：静态站点负责可直接访问的技能信息与发布 feed；技能源负责安装所需的正文。前者可用不代表后者必然公开。若安装正文位于非公开仓库，Agent 复用员工已有仓库认证，缺失时明确报告该来源的访问要求，不要求为查看技能信息预先配置 Token。

Pagefind 构建时索引技能详情的名称、用途、示例和关键词，排除导航与所有技能重复出现的安装样板。layer、Agent、来源和发布时验证状态作为筛选维度；关键词为空时仍允许按筛选浏览。首版中文页面统一语言标记，避免中英文技能被语言分库意外隔离。官方文档说明 CJK 分词需要 extended 版本，支持分词不等于已经满足本项目检索质量。[Pagefind 多语言](https://pagefind.app/docs/multilingual/)、[筛选](https://pagefind.app/docs/filtering/)

同义词与缩写由 `curation/` 提供小型映射，构建时补充检索词；中文目的、英文技能名、混合查询和无结果路径必须实测。相关技能先按目的和标签确定性计算，主题精选由维护者批量审阅。不接入向量库或搜索服务，除非检索质量/规模测试证明静态索引不足。

卡片可直接复制安装提示词。普通用户不选择 revision；默认指向已验证版本，未验证项展示真实状态。提示词引用发布版本中的安装说明，安装说明引用已解析来源；最终安装报告实际版本。hosted 来源用发布构建的源 commit 定位正文，不把自身 commit 写入同一次提交而形成自引用。

Agent 自动判断可确定的目标环境，默认项目级；依赖账号、授权和重启等不能自动满足时给出最短具体操作。安装检查须覆盖完整目录、识别情况和冲突处理，完成后提供可复制的首个任务示例。未知上游安装方式只提供明确状态与人工指引，不输出猜测的命令。

## 7. 构建、发布与版本一致性

不把“PR 合入”直接等同于“可以通知”。发布流程：

1. CI 从固定源 commit 读取条目，以及固定摘要的验证/来源解析快照；在构建前持久化一次候选发布上下文，冻结首次发布时间及已发布身份映射，重试复用。
2. Python 验证并生成规范化 catalog、安装材料和内容摘要；同样输入应产生同样正文产物，执行时间等放在外层发布信息。
3. Astro 生成网站，Pagefind 索引；检查详情、安装说明和索引引用完整。
4. 上传不可变目录 `releases/<release_id>/`，其中 release ID 由源 commit、验证/来源解析快照摘要、构建配置身份和冻结的发布上下文共同确定；重试复用候选记录，不重新生成首次发布时间。
5. 对该目录执行实际读取检查，通过后切换网站入口；最后写入已发布日志。发布任务串行化并拒绝较旧发布覆盖较新入口。首次发布时间采用这次成功提交日志对应的候选发布时间，精确提交时间另记 committed_at。
6. 日志写入失败时，下次任务先恢复同一候选发布，幂等补写后才推进新发布；已发布日志引用保留的不可变目录，群通知不依赖随时变化的 latest 链接。详细恢复和事件身份见第 17 节。

网站构建器不实时拉取外部正文，避免某个上游失败阻塞全站发布。验证报告采集失败保留上次数据及其时间，网站显示过期，不把失败当作零值。Star 首版采用可选动态 badge，不加入构建采集流程，具体边界见第 13 节。

发布日志为持久的追加记录，含单调 sequence、release ID、源 commit、前序记录、事件列表、安装说明 URL 和产物摘要；发布状态不依赖会自动过期的普通 CI 临时 artifact。首选组织静态发布存储并直接提供无需 Token 的 feed。若实际部署改用仓库作为读取入口，则由蓝区发布身份把成功记录写到同仓独立发布分支，该分支排除源码 CI 触发；高区只读，只有非公开仓库需要读取 Token。具体仓库适配必须按实际 Git 平台确认接口与权限。

新增和重要更新事件以相对上次发布目录的语义差异生成；推荐帖使用独立 recommendation ID，首版不再额外维护 campaign 实体。仅验证报告变化不重新发“新技能”。回滚切换网站入口，不删除已发日志；需撤回时追加撤回事件，信息模块输出前检查最新撤回状态。

## 8. Python 信息提供模块

本期实现到信息提供为止，不建设 GroupSender、Webhook 发送器、bot 桩、平台签名/卡片或群回执模型。模块可由既有调度器周期调用，也可作为 Python 库由后续 bot 接入代码调用。

职责限定为 `FeedReader`（读取固定发布快照）、校验/规范化、筛选与增量比较、`ChangeStore`（本区状态）和 JSON 输出。提供稳定输出字段及批次交接边界，后续使用 SDK 还是 HTTP 提交给 bot 不影响数据处理核心。

默认从静态 feed 无 Token 读取；直接读取非公开仓库时按仓库适配方式配置只读权限。凭据不进入输出或日志，认证头不随跨域重定向转发。获取不执行 feed 中的脚本或任意指令。

SQLite 保存来源游标、去重信息和待交接批次，采用本区本地持久卷、单实例执行和原子事务；读取进度与已确认交接进度明确区分。具体输出和确认语义见第 17 节。此状态不是群投递数据库，不包含群消息 ID、发送状态机或平台限流配置。

容错覆盖读取超时/限流/临时失败、认证失效、数据不完整、未知 Schema、增量缺口、重复数据、文件输出失败与重启恢复。临时读取失败退避重试，确定性格式错误不无限重试；不成功时保留原交接进度。通过 fixture 或本地 feed 服务测试，不需要 bot 模拟服务。

## 9. 验证与动态数据

现有 `test_runner.py`、Docker runner、fixture 和 artifact 管理可复用，但当前运行契约围绕 Profile/Search/Load，原结果不能当作新安装路径的证据。新增原生安装 collection，覆盖至少一个 hosted 和一个 external 技能。

验证报告包含 `skill_id`、源版本/内容摘要、安装声明摘要、Agent 版本、操作系统、runner 身份、执行时间、层次结果和证据链接。验证任务用固定源版本，临时获取外部正文并清理；安装目标为隔离目录，不能修改运行器宿主配置。

PR 默认只跑无凭据的确定性门禁；外部获取与带 Agent 的执行进入受控任务。先审阅执行输入再向验证环境配置所需凭据，不能让任意投稿脚本直接取得发布或群凭据。现有 command-only 容器禁网规则意味着外部获取需要单独准备阶段，不能照搬原 runner 就宣称完整安装验证可用。

验证结果保存到持久报告存储；索引由固定报告快照加入下一次网站构建，因此筛选和详情状态一致。首版可每日汇总巡检后触发一次构建，急需撤回时立即发布；过期报告明确带时间。Star 首版只用 badge 展示，不维护数值快照或排行。

验证调度键包含所有影响结果的版本身份，只测受影响项。外部可用性随时间变化，过去获取成功不能永久免除巡检。安装/行为结果可历史复用，但发布新版本须展示是否重验。

## 10. 现有系统迁移

当前 `SkillRecord` 必须持有本地 `Path`，`registry.validate_skill` 必须读取 `SKILL.md` 并计算摘要，`validate_registry` 同时校验 Profile；这与外部仅引用模型冲突。因此新增目录模型，不把 URL 填进旧 path，也不直接修改旧 catalog 格式。

已确认采用同仓库换代：保留仓库入口与历史，在新版分支建设，旧版用固定标签保存，最小闭环可用后迁移 PR 切换主线。不新建仓库，不长期保留 legacy 目录或旧运行时兼容层。只有以后出现独立产品维护、组织归属或权限域变化时，才重新评估拆仓。

迁移顺序：

1. 选定旧实现基线 commit 并建立固定标签，记录旧版使用方法与真实验证状态。标签名在实施时确定，不把本文当作已创建标签的证据。
2. 将两份新规格独立纳入 Git，在新版开发分支建设新结构，主线在切换前保持旧版可用。新分支默认采用 codex/ 前缀，具体名称在实施时确定。
3. 从 manual 生成 hosted 条目，从 upstream 来源生成 external 条目；转换脚本只生成候选变更，列出无法解析的路径、来源和安装方式。选择性迁移公共代码，不要求新版继续承载旧运行时。
4. 完成贡献流程、网站发布、静态信息读取、干净 Luna 至少一例 hosted 和 external 实际安装、独立推荐与发布事件，以及 Python 增量信息输出的最小闭环。bot 提交方式后续确定，不阻塞本期迁移验收。
5. 通过迁移 PR 切换主线，同时更新 README、安装入口、依赖和测试，清理旧 Profile、Hook、MCP、加载器、外部快照及其引用。不仅删除正文而保留失效命令或测试。
6. 旧功能从固定标签继续获取，新主线只维护新的目录与分享产品。保留旧版入口、迁移说明与回退指引，不重写 Git 历史。

| 内容 | 新版处理 |
| --- | --- |
| 自研技能正文 | 保留并纳入 hosted 模型 |
| 外部技能快照及旧 source manifest | 转换为 external 条目后从新版工作树清理，历史仍留在旧版本 |
| digest.py、frontmatter.py、git_source.py 等工具 | 按新调用边界选择性复用，连同必要测试迁移 |
| 旧 Profile、Hook、MCP、CLI 与加载器 | 切换时移除退出范围的代码、依赖和命令，不长期兼容 |
| Demo、Docker 与旧测试集合 | 借鉴可用设施，按新安装路径重建，不能整套继承旧验证结论 |
| 新规格与设计 | 保留为新版依据 |
| 旧规格与计划 | 从旧标签/历史查阅，新版只留必要演进索引 |

旧 install.sh 入口当前跟随 main；迁移验收必须确认旧版入口真正锁定代码获取目标，而非仅把脚本 URL 指向旧标签、内部却继续获取 main。需要时提供单独的固定版本安装说明，不移动旧标签去补丁修复。新版不得把旧用户配置自动解释成新目录配置，也不得自动卸载其已有技能。

切换验收包括无悬空引用、旧依赖退出、新入口可用、旧标签可取、迁移说明完整。保留旧标签不等于承诺永久适配以后发布的宿主版本；文档应明确旧版原验证环境。

## 13. 后续推荐与免采集 Star 展示

### 13.1 推荐帖独立于技能条目

技能条目回答“是什么、如何安装”；推荐帖回答“为什么值得尝试、适用于什么任务”。同一技能允许多个作者或在不同时间推荐，一篇主题推荐可关联多个技能。推荐不要求技能正文或版本发生更新。

首版只增加一个人工维护实体 `Recommendation`，仍使用 Git YAML、Schema、Agent 辅助投稿和 PR 审阅。发布事件与信息交接状态分别保存在发布日志和各区 SQLite，不另建推荐业务数据库。点赞、收藏或推荐人数是另一类交互记录，首版不因推荐帖而引入这些计数。

推荐帖字段：

| 字段 | 含义与维护方式 |
| --- | --- |
| `schema_version`、`id` | Schema 版本及稳定帖 ID，由 Agent/工具生成 |
| `skills` | 一个或多个技能引用；至少含 `id`，可选实际体验版本 |
| `title`、`body` | 推荐标题与内容；至少说明一个具体用途，员工可只给一句理由 |
| `author` | 作者或团队的可公开标识；由投稿上下文确认，不根据提交邮箱擅自公开身份 |
| `topics` | 可选用途标签；默认从关联技能派生 |
| `evidence` | 可选的可发布案例/证据链接；无证据不能生成“实测提升”等经验断言 |
| `status` | draft、ready 或 withdrawn；ready 表示请求发布，实际发布由流水线成功结果决定 |

`published_at`、内容 revision 和实际事件 ID 由发布流程生成，不要求作者填写；信息交接状态由各区 Python 任务维护。新 ready 帖必须引用同一候选发布中存在且 active 的技能，允许新技能与其首篇推荐在同一 PR 中新增；不要求先发布技能再提交第二个 PR。草稿可暂时引用待收录候选，草稿不输出到网站。可选体验版本只描述作者当时环境，不自动改变技能当前安装默认值或验证状态。

示例（格式示意，所引用技能需存在）：

```yaml
schema_version: 1
id: review-gitcode-diffs
skills:
  - id: local/gitcode-pr-review-fetch
title: 检视 GitCode PR 时先拿到完整差异
body: 适合需要一起查看代码差异、行级评论和讨论回复的检视任务。
author: directory-team
topics: [代码检视]
status: ready
```

员工可复制“请按贡献指引，为〈技能链接〉发布一篇推荐，理由是〈一句话〉”。Agent 生成新帖、检查引用、准备 PR；同一技能已存在不阻止新推荐，只提示近期相似内容，避免误把正常后续推荐当作重复技能。

初次贡献的可选推荐理由也可由工具生成一篇 Recommendation，不在技能条目和推荐帖中长期手工维护两份正文；早期草案的 `entry.recommendation_reason` 只允许输入转换器读取并移出，不属于正式 SkillEntry v1 Schema。没有理由时只发布新增技能事件，不凭空生成作者推荐。

### 13.2 发布、编辑、撤回与触达

网站增加推荐列表和 `/recommendations/<id>/` 详情，技能详情反向展示关联推荐。主题推荐复用同一模型，`curation/` 只维护精选选择、主题定义与同义词，不重复保存推荐正文。

推荐帖第一次从未发布状态进入成功发布版本时生成 `recommendation.published` 事件；事件稳定关联推荐 ID 与首次发布身份。普通编辑更新网站，不生成重复推广。需要再次推广时创建有新理由/案例的新帖。删除已发布帖不替代撤回，使用 withdrawn 更新网页并追加撤回事件，信息模块排除尚未交接的已撤回推广。

同次发布里新增技能及其首次推荐可合并为一个信息条目，保留关联事件 ID；后续推荐独立输出。同一帖子关联多个技能也只生成一个主题条目。输出不包含特定平台群卡格式；群目标、发送频率与提交策略由未来调用方决定。

首页“最新推荐”按实际首次发布时间排序，编辑不刷榜。页面可以显示“推荐文章数”，不能把文章数当作推荐人数。未来需要“多少人推荐”时另按经确认的作者身份、技能和区域去重，且不默认跨区合并。

蓝区网站只能发布允许进入蓝区的推荐内容。高区推荐继续留在本区入口；如后续需要本区推荐 feed，可复用 Schema 和信息获取逻辑，但必须增加区域来源命名空间，不能默认复制到蓝区 Git。

### 13.3 Star badge 优先方案

如果只展示上游 Star，推荐直接嵌入受支持的托管动态 badge，由服务提供方读取来源并缓存图片。本项目不定时采集、不存数值、不因数量变化重建网站。这是免自行采集维护，并非保证服务永久可用或数字实时准确。

Shields.io 提供 GitHub Repo stars 和 GitLab Stars badge，后者明确要求 GitLab 实例可从互联网访问；GitHub badge 支持缓存时间参数且低于其默认策略的值会被忽略。[GitHub Star badge](https://shields.io/badges/git-hub-repo-stars)、[GitLab Star badge](https://shields.io/badges/git-lab-stars)

公开 GitHub 仓库的图片 URL 模板：

```text
https://img.shields.io/github/stars/<owner>/<repo>?style=flat&label=GitHub%20Stars
```

网站用来源信息自动生成 URL，外层链接指向原仓库，标注“上游仓库 Stars”。多技能同仓共用同一数值；不解释为单技能评分。页面使用图片元素展示，不把远程 SVG 内联为可执行内容，不向 badge URL 放入任何 Token。

展示策略由部署配置统一控制，如 `stars_display: auto|off`，不要求每个贡献者手填图片链接。auto 仅对显式标记为公开且受支持的来源启用；其余显示原仓库链接。来源无法确定是否公开时关闭 badge，不能把内网仓库定位自动提交给公共图片服务。

| 情况 | 首版处理 |
| --- | --- |
| 公开受支持来源，用户浏览器可访问图片域名 | 直接动态 badge；核心页面和安装不依赖图片加载成功 |
| 公开来源，但所在区域无法加载外部图片 | 关闭 badge，保留原仓库链接，不为 Star 单独建服务 |
| 私有/内网 Git 来源 | 仅使用已有、可访问且不会暴露凭据的组织 badge 服务；没有就不展示数值 |
| GitCode 或其他尚未核实支持的来源 | 不猜测 endpoint；先保留来源链接，后续核实官方 badge 或公开计数接口 |

Shields 的 Dynamic JSON Badge 可以从可访问 JSON 中提取值，但仍需稳定的数据接口；私有源、认证和跨区网络问题不会因图片形式消失。自托管 Shields 虽可部署在内网，仍需运行、升级、凭据及数据源维护，不作为“免维护”默认方案。[动态 JSON badge](https://shields.io/badges/dynamic-json-badge)、[自托管入口](https://shields.io/)

badge 异步、按需加载，缺图时回退到来源链接；某些服务错误会返回正常 HTTP 状态的错误图片，首版不宣称可自动识别所有数值错误。不标注本平台未掌握的采集时间，说明数值由第三方缓存更新。

badge 仅作为展示装饰，不解析图片取得数值，不加入 Pagefind 排序、排行榜、趋势或推荐分。若将来确需这些功能，再新增带 `value`、`source`、`fetched_at` 的结构化采集快照并承担相应维护成本。

新增验收：同技能可发布第二篇推荐；一帖关联多技能只输出一个主题条目；改正文不重复推广；首次收录和推荐合并；撤回过滤未交接推广；badge 禁用/不可达不影响搜索、安装或网站发布；不显示未经采集的 Star 排名或更新时间。

## 14. 数据提交与 PR 契约

### 14.1 三类变更与权限

| 意图 | 最少输入 | 变更范围 | 提交结果 |
| --- | --- | --- | --- |
| add-skill | 技能来源或本地目录 | entries；hosted 加正文；有理由可加推荐帖 | 一个包含全部关联文件的 PR |
| add-recommendation | 技能 ID/链接＋一句理由 | recommendations；多个技能只生成一篇主题帖 | 推荐 PR，不改技能版本 |
| correct-entry | 技能 ID/链接＋修正内容 | 指定条目及必要引用 | 修正 PR，不创建重复 ID |

贡献指引声明支持的 Schema 版本、目标仓库、默认目标分支获取方式、检查入口和模板位置。Agent 从实际仓库读取默认分支，不硬编码 main。准备时记录 base_commit；提交前更新目标基线并重跑全量引用/重复校验，避免两人同时收录同一技能。ID 冲突不自动覆盖；语义重复返回已有条目，分类移动不改变 ID。

员工已有授权可覆盖提交，不要求每阶段重复确认。仍需实际写入权限：同仓分支优先，平台只允许 Fork 时走 Fork PR。首次贡献的本地生成、本地 commit、已推送分支和已创建 PR 分别报告，只有真实 PR URL 才能标记“已提交”。没有凭据时返回本区补丁和检查结果；不得把凭据放入网站、提示词或补丁。

提交到 Git 与向已有群/表单发送反馈是不同动作；本项目不授予 Agent 任意发消息权限。自动接收/反馈需由已经配置并获准的入口处理。

### 14.2 本地检查接口（拟实现，不是当前已存在命令）

新目录工具使用独立模块入口，不要求安装旧 MCP/Hook 运行时：

```text
python -m hwskill.directory validate --repo-root <path> --json
python -m hwskill.directory build --repo-root <path> --out <path>
python -m hwskill.directory migration-preview --repo-root <path> --out <path>
```

validate 不修改文件，默认检查所有条目、推荐与跨文件引用。build 校验通过后原子生成新产物目录，不修改人工源文件。migration-preview 只产生候选变更和无法自动转换的清单，不删除旧快照。工具运行依赖可在贡献工作目录隔离安装，无需员工自行配置平台运行时。

校验报告固定包含 `schema_version`、`source_commit`、`input_digest`、`result`、`issues`；input_digest 覆盖实际待校验条目、正文及 Schema，区分同一 HEAD 下的未提交修改，source_commit 在无 Git 环境时可为 null。每个 issue 按第 4 节字段输出。退出码 0 表示确定性校验通过、1 表示输入不合格、3 表示环境受限；缺依赖不能误标为条目格式失败。报告没有执行安装测试时必须显式列明，不输出总括的“技能验证通过”。

PR 描述由工具/Agent 按同一格式整理：变更意图、关联 ID、来源依据、检查摘要及未验证项、投稿接收记录的可公开引用。CI 重新校验实际 PR head 和目标分支的候选合并结果，不接受投稿者上传的成功报告替代检查。head 更新后旧报告不再满足合入门禁。

元数据提交只允许预期内容路径；若 PR 同时修改 Schema、CI、构建器或执行入口，应作为基础设施变更单独审阅，不能用内容校验代替代码审阅。发布凭据不进入投稿分支的任意可执行任务。

### 14.3 门禁与工作状态

硬门禁：Schema/ID/路径/引用一致、hosted 必要文件完整、构建成功、无未处理冲突。软状态：缺少真实安装证据、许可证未知、外部访问受限；如实展示并允许维护者按条目情况收录，不能由 CI 编造兼容承诺。

投稿状态使用 PR、CI 和发布记录派生，不新增用户手填状态机。ready 是内容发布意图，merged 是 Git 状态，published 是发布日志状态，三者互不替代。PR 关闭未合入不产生内容事件；合入后构建失败保留发布任务错误，修复/重试由维护流程承担。

## 15. 数据实体与状态契约

### 15.1 SkillEntry v1

以下字段是实现 Schema 的规范输入，详情措辞由需求规格限定：

| 字段 | 结构与默认策略 |
| --- | --- |
| schema_version、id、name、summary、layer | version=1；ID 为 namespace/name；layer 为 l1–l5 |
| purposes、examples | 非空数组；示例含 prompt 和 expected_outcome，不把预期结果写成已验证事实 |
| source | hosted: kind/path；external: kind/locator/publicity；publicity 为 public/private/unknown，默认 unknown |
| source.locator | git: type/repository/path/requested_ref；非 Git: type=web/url，允许补充上游版本说明 |
| install | method 为 directory/upstream/unknown；default_scope 为 project；影响的附带技能可选列出 |
| install.instructions_url | upstream 方法必须提供明确上游指引；unknown 不生成自动安装动作 |
| compatibility | agents、systems 与 requirements；未知用显式 unknown，空依赖表示明确无需依赖 |
| license | 状态 known/unknown；known 时填 identifier 或说明链接，unknown 不伪造许可证 |
| owner、keywords、limitations | owner 可继承目录配置；关键词与限制可选，无需每条写相同 owner |
| lifecycle、lifecycle_reason、replacement_id | active 默认；deprecated/withdrawn 必须说明原因，替代 ID 可选且需存在 |

源 YAML 缺省项在规范化输出中补全，类型不混用“缺字段”“null”和字符串 unknown。Schema 对指定结构拒绝未知键，避免拼错字段被忽略；扩展先升级规范。原始 source 引用与正文摘要按各自职责保存，不把抓取时间写成内容版本。

目录发布包含 active/deprecated/withdrawn 的说明记录，安装能力据第 16 节派生。当前撤回状态须在稳定状态索引中可查询；历史不可变安装材料不能代表今天仍可用。生命周期修改不自动更改员工本地文件。

### 15.2 Recommendation v1

字段沿用第 13 节。新帖可直接创建为 ready，不要求额外提交草稿 PR；未发布时允许 draft 与 ready 相互转换，draft 可直接删除。已发布 ready 只能保持 ready 或转为 withdrawn，不能改回 draft 来绕过撤回记录。withdrawn 为同一推荐 ID 的终态，再次推荐用新 ID。ready 普通编辑保留首次发布时间，不触发新发布通知。

草稿仍接受结构检查，未解析的候选引用只在草稿层允许，不能出现在最终 catalog、recommendations JSON、Pagefind 或用户可访问的构建产物中。已发布内容消失的提交必须转为明确撤回或附迁移记录，不能靠删除造成历史链接丢失。

已有帖子引用的技能后来弃用/撤回，不阻止全站构建；保留历史推荐并派生 `promotion_eligible=false`，标记关联技能状态并停用对应安装按钮。新帖不得主动推荐已撤回/弃用技能。此规则只影响主动推广，不自动改写作者的历史正文。

### 15.3 输出物与所有权

| 对象 | 谁写 | 消费者 | 持久位置 |
| --- | --- | --- | --- |
| SkillEntry、Recommendation、主题配置 | 员工 Agent/维护者，经 PR | 目录构建器 | 蓝区源 Git |
| 解析来源快照、VerificationReport | 受控获取/验证任务 | 构建器及安装解析 | 蓝区持久产物存储 |
| Catalog、推荐索引、安装材料 | 固定版本构建器 | 网站、员工 Agent | 不可变 release |
| 发布候选与发布日志 | 串行发布任务 | 网站状态、区域任务 | 持久发布存储或发布分支 |
| 信息批次、关联事件与交接进度 | Python 信息模块 | 后续消费者及运维 | 本区 SQLite/JSON 输出 |

规范化 Catalog v1 包含 schema_version、source_commit、entries；每条含原始规范化描述、entry_digest、lifecycle、安装能力和验证摘要。推荐索引与 Catalog 使用相同 release ID，并以 skill ID 关联，不复制技能来源和安装命令。

输入文本渲染时进行转义，只支持有限 Markdown；构建器将模板代码与投稿内容分离，外部技能正文不参与网站可执行模板。JSON 和 Markdown 安装材料同源生成，测试其 ID、版本、范围和 URL 一致。

## 16. 安装能力与验证适用性

### 16.1 解析与默认值

构建过程无隐式公网请求。hosted 用源 commit 与内容摘要定位；external Git 使用获取任务生成的来源解析快照，快照绑定 locator 摘要、requested_ref 和实际 revision。安装说明使用该固定 revision；没有快照时只允许显式的未锁定来源指引，不标记为可复现或已验证。

已验证版本默认值按目标 Agent/系统选择：必须与当前技能身份、安装声明摘要、目标环境匹配，且未被撤回。若声明新的 requested_ref 或安装方法，不能继续把不匹配的旧验证记录当作当前默认通过；网站可单独列出历史可用版本。

| 派生能力 | 条件 | 页面行为 |
| --- | --- | --- |
| installable | lifecycle 允许安装，来源定位和方法明确 | 复制安装提示词；单独展示验证状态与是否锁定版本 |
| guidance_only | 安装方法 unknown，或只有不能自动定位内容的上游说明 | 展示来源和待完善原因，允许贡献修正，不生成猜测命令 |
| temporarily_unavailable | 最近有效探测表明来源不可获取 | 展示失败与检查时间，提供原来源/替代入口，不显示保证可安装的措辞 |
| disabled | lifecycle=withdrawn | 停用安装入口，展示撤回说明 |

弃用但未撤回的技能可保留历史安装入口，显式提示原因和替代技能，不默认精选。探测记录缺失只表示未知，不能自动认定来源不可用。

稳定状态索引供 Agent 在使用历史安装说明前检查当前 lifecycle；当前状态无法读取时报告状态未确认，不能声称已经检查撤回状态。已知撤回时必须停止新安装。已复制文本和历史 Git 内容无法远程收回，文档不保证全局强制卸载。

### 16.2 VerificationReport v1

报告包含 report_id、skill_id、source_identity、entry_digest、install_digest、host/version、os/arch、runner_identity、executed_at、stages 和 evidence_refs。stages 分别为 metadata/acquisition/installation/behavior，每阶段 result 为 pass/fail/blocked/not_run，并说明原因。freshness 使用独立 expires_at 或部署侧时效策略表达，不把历史 pass 改写成执行失败。

报告与技能版本或安装声明不匹配时仅作为历史展示。entry_digest 用于追溯整条元数据；只修正展示文案或分类不强制重新安装验证，适用性以源身份、安装摘要、环境和时效为准。搜索的“安装已验证”筛选要求至少一个明确展示的组合通过 installation；员工选择 Agent 后按该 Agent 过滤，不将一个组合通过扩展到全部宿主。behavior 通过须同时有相同适用组合的安装证据；用户可读取完整矩阵。

local 校验无执行证据不能生成 installation/behavior pass。每次真实安装测试需包含完整文件、宿主识别、重复安装、已有同名内容、失败后保留无关配置等用例；一般外部技能不保证有统一行为验收任务，无行为证据仍可标注安装验证通过。

安装测试记录不默认回收员工会话、文件和使用行为。来源获取失败按源聚合，同源多个技能共享一次可用性探测，避免重复请求和重复告警；源码或安装声明变化才扩大重验范围。

## 17. 发布恢复与增量信息交接契约

### 17.1 发布身份与状态

发布流程持久状态为 prepared → uploaded → checked → activated → committed；失败保留所在阶段与错误，重试相同候选，而不是重新生成逻辑事件。候选记录包含 release_id、previous_committed_sequence、输入摘要、预分配的 publication_time、站点目录和事件清单。所有时间按 UTC 写入，网页再按展示时区格式化。

首次发布时间使用成功 committed 的候选记录时间，精确提交时间使用 committed_at；失败候选不对外声称发布成功。这样静态页面构建时即可使用稳定时间，无需把“发布后才知道的时间”反向写入同一次构建。

release_id 对包括冻结发布上下文的构建输入唯一。相同源/快照/配置的发布请求优先查找已有候选或成功产物，不能仅换一个时间重建同一内容并重发。部署为已经 committed 的 release_id 时不追加内容事件。站点回滚不回滚发布日志、事件历史或各区 cursor。判断“首次推荐/首次技能”用持久发布历史，而非仅比较当前回滚站点，避免重新升级时刷出重复新增事件。

prepared 后站点尚未切换的失败可安全重试；activated 后日志写入失败须先完成或明确撤销候选恢复，再允许后续发布。先写不可变日志记录，最后以支持原子更新的指针/分支头暴露新的 sequence；部分上传不进入可消费范围。发布存储适配器必须提供单写者约束与原子可见性，不能依赖多文件普通覆盖模拟事务。

### 17.2 事件契约

每个已提交事件包含：schema_version、feed_id、event_id、sequence、release_id、type、subject_id、subject_revision、skill_ids、published_at、page_url 和 machine_url。序号属于发布日志；同一记录内事件按 ID 排序，分页返回完整已提交记录及对应校验摘要。

type 首版为 skill.added、skill.updated、skill.withdrawn、recommendation.published、recommendation.withdrawn。skill.updated 只用于安装来源/方法、生命周期或重要可用性变化，不将正文排版和每次巡检时间当作通知。恢复已撤回技能需新的审阅发布，产生更新事件，不复用曾经的新增事件。

event_id 用 feed_id、type、subject_id 和逻辑变更身份生成。新增技能/首次推荐以固定的首次发布身份生成一次；更新/撤回以该主体上一逻辑事件 ID、当前语义摘要及变更类型生成，身份在候选记录冻结。单纯部署回滚不制造内容变更；以后经新 PR 真正再次弃用/恢复时可形成新的状态迁移事件，不能因内容曾经出现过而漏掉通知。重试同一候选不重新发明 ID。既有 ID 的事件正文不可被覆盖；更正是新事件，不是篡改旧记录。

feed_id 在本次部署长期稳定；未来本区推荐 feed 必须使用另一命名空间。消费者遇到未知重大 Schema 版本、sequence 缺口、摘要不符时停在可恢复位置并告警，不直接跳到最新。

首次初始化必须由部署配置显式指定建立基线，记录 feed_id、基线 sequence 和初始化标记；常规轮询发现状态库缺失时返回需要恢复，不能自动套用首次启动策略。接收记录与最新撤回快照同时取自固定 feed head，避免初始化时漏掉既有撤回状态。

首版建议保留全部发布元数据日志，不将外部正文纳入存储。上线前配置历史发布页面/安装材料保留策略；清理前保证旧链接能返回历史或明确撤回/过期说明，不能默认按 CI artifact 保留时间自动删空。

### 17.3 信息批次与确认

输出按消费者配置生成，不把“消费者”绑定为群：它可以是后续 SDK 程序、HTTP 提交脚本或人工检查流程。同一消费者固定 feed_id 和筛选配置身份；改变筛选条件需明确建立新基线或指定回看范围，不能悄悄漏掉过去被过滤的信息。

拟提供两个小接口：`prepare_updates` 返回待处理批次，`acknowledge` 确认指定批次已被调用方接收。另提供同语义 CLI/JSON 导出；具体参数在实施计划中固定，不在本期加入 bot transport 插件体系。

批次含 schema_version、consumer_id、batch_id、feed_id、from_sequence、through_sequence、filter_digest、snapshot_identity 和 items。每个 item 含稳定 ID、关联事件 ID、变更类型、技能/推荐引用、标题摘要、来源版本、详情和安装说明链接、生命周期。文本只为通用信息摘要，不解释为平台 Markdown 或群卡。

以已确认游标到固定 feed head 的完整区间做校验、筛选、去重和合并。新收录与同次首篇推荐合为一个条目；多技能推荐保留一个主题条目。读取批次内的最新状态后再过滤推广，不输出已经撤回/弃用的主动推荐；撤回本身作为控制变化输出。即使所有信息被过滤，也返回可确认的空 items 批次以显式消费该区间。

批次及其输入身份在本区事务中持久化，确认前不推进交接游标。同一输入重复准备产生相同 batch_id；导出成功只表示文件写出，必须由调用方确认接收。只允许确认当前待交接批次的精确 ID；重复确认同一已确认批次幂等，过期/错误 ID 拒绝。

确认前重复 prepare 会检查最新来源快照；快照未变时返回原批次，新增撤回等变化时可用更新快照重算未确认区间并产生新 batch_id，旧批次确认被拒绝。输出标明基于哪个快照，不承诺已经导出的旧文件能远程失效；实际调用方应取得当前批次后使用。交接确认与发送原子性、群去重和发送成功判定属于后续 bot 接入职责。

SQLite 最小保存消费者已确认游标、已确认批次身份及当前 pending batch。批次准备与确认均采用单实例锁和事务；输出文件采用临时文件完成后原子替换。失败、未知版本或区间缺口保留原游标，重启可恢复 pending 内容。首版不增加 deliveries、群消息状态、签名、发送回执和 bot 本地桩。

容错测试包括连续两次读取、空增量、过滤后空批次、同次收录与推荐合并、普通编辑不产生新推广、撤回重算、旧 batch 确认拒绝、重复确认、写出失败、事务中断和缺失状态库。初始化须明确选择从当前建立基线或回看指定范围；常规运行发现状态丢失时报告需要恢复，不自动当首次启动。

## 18. 联调与交付门槛

| 契约用例 | 必须证明的结果 |
| --- | --- |
| 同 PR 新增技能与推荐 | 引用检查通过，正式发布合并成一个信息条目 |
| 两 PR 同时收录同源技能 | 第二个候选合并校验发现重复，不能静默覆盖 |
| 推荐普通编辑/撤回/重新创建 | 编辑不重发，撤回终止旧帖推广，新帖独立发布 |
| 草稿及未知字段 | 草稿不泄露到发布索引，拼错字段被校验拒绝 |
| 条目与报告版本不匹配 | 页面不展示当前安装验证通过 |
| 安装仅一个宿主通过 | 指定该组合展示，不扩展为全宿主通过 |
| 站点切换后日志写失败 | 恢复同一候选，不漏写或重复通知 |
| 回滚后再次部署历史版本 | 发布历史不回滚，首次推荐不再次刷出 |
| 信息合并与进程重启 | 未确认批次可恢复，不静默推进交接游标 |
| 过滤后空批次与重复确认 | 可显式消费区间，确认幂等，不漏掉后续数据 |
| 未确认批次新增撤回 | 重算当前批次，拒绝旧 batch ID，不继续输出撤回推广 |
| 日志缺口或数据库丢失 | 明确恢复流程，不自动当首次运行吞掉未处理信息 |
| 静态 feed 与非公开仓库读取 | 静态模式不要求 Token、不发送认证头；仅私有仓库模式需要读取权限 |
| badge 无网络或错误图片 | 核心页面可用，不把错误解释为零 Star |
